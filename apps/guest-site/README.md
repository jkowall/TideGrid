# @tidegrid/guest-site

The branded guest site for the demo build: one React and Vite build serves every operator, which the API names from the page's Origin, with that operator's validated brand. Pages: `/` (the operator's upcoming trips, G2.11a), `/book/<tripId>` (the checkout, G2.11b), `/manage` (the booking's management page, G2.11c), the placeholder legal pages (also at `/terms` and `/privacy`), and `/support` and `/offline` (G2.14b). The site moves between its own pages in place, through the History API, so the brand stays on screen; Back and Forward work.

## The checkout (G2.11b)

The minimal guest checkout in the [demo build plan](../../docs/v2/12-demo-build-plan.md#goal-sequence). It consumes the pricing and checkout API unchanged ([pricing contract](../../packages/domain-pricing/README.md#api), [checkout contract](../../packages/domain-booking/README.md#api)).

1. **Party.** A trip's Book link carries the list's party size. The page loads the trip's offer and its listing (meeting point, seats left, cutoff), then asks for tickets per type or, for a charter, guests aboard, and any extras. It shows unit prices, fees, how tax is added, and the cancellation policy, but no totals: the server prices everything. A count past a limit stays as typed, with the reason beside it ("Only 4 seats are left, and your party is 6"); the page never lowers a party by itself. Extras follow the party once its count is final (a button, leaving the field, or sending the form), not on every keystroke, since typing 12 passes through 1; the page says aloud when a smaller party lowers an extra. Sending the form prices exactly the counts the fields show.
2. **Details.** `POST /v1/public/quotes` prices the party. The page shows the itemized quote (lines, subtotal, discount, fees, added taxes, total, and any tax already included) and when the price expires. The discount row says it comes off the trip price, not extras. A promotion code is applied as a new quote; a refused code marks its field and keeps the current price. The guest gives a name and email and accepts the policy version shown.
3. **Payment.** `POST /v1/public/checkout-sessions` opens the checkout and holds the seats; the trip's facts then say so ("Your 3 seats are held"). The demo pays through the fake provider: the page says plainly that this is a test payment and no real card is charged, and offers "Simulate successful payment" and "Simulate declined payment". Cancel checkout asks first, in a dialog, then releases the seats at once.
4. **Outcome.** The page reads `GET /v1/public/checkout-sessions/{id}` with a gentle backoff until the state is final. Confirmed shows the booking reference, trip, place, party, extras, and total. Declined offers Try again (a new quote and a new checkout, keeping the details). Expired and canceled offer Start over with the same party. Unfulfilled says the payment came after the checkout could no longer become a booking, gives a short checkout reference to quote, and follows the refund.

**Only the server decides.** A payment button only asks the provider to settle; its answer is ignored except as "sent". The confirmation appears only when the checkout's own state says confirmed. Once a payment was sent, or may have been, no screen says that nothing was charged: an expired checkout is read for a short grace in case a late success books it, and the copy says that such a payment is booked or refunded in full.

**The server's clock.** Every deadline on the page is an instant on the server's clock. The page learns the offset between the device and the server from a new quote's `quotedAt` and a new checkout's `createdAt` (never from a replayed answer), so a device clock that is minutes or hours off neither expires a fresh price nor says a live hold has run out (`src/booking/clock.ts`).

**Commands and keys.** Creating a quote and opening a checkout carry an `Idempotency-Key`. Sending the same request again after no answer, a 503 `payment_provider_unavailable`, or another error reuses the key (and, for a checkout, the same checkout secret, since the body must match); any request after a success, or with a different body, is a new command with a new key. A checkout whose answer was lost locks the page until the same request goes again: the price, the code, and the party can't change, Back stays, and a link away asks first, so a second checkout cannot open beside the first. A definite answer to the retry unlocks it, since nothing was written under the key; a rate limit does not, because the API refuses it before reading the key. Canceling a checkout and settling a test payment take no key in the API: both are idempotent by their resource, so a retry sends the same request.

**Back, Forward, and leaving.** Moving on from the party and from the details adds a history entry, so Back returns one step and Forward comes back to a price that still holds. Back from the payment asks to cancel the checkout first, as Cancel checkout does; Back while a payment is being confirmed stays and says why. A link to another page of the site asks first when a checkout is open and unpaid, is still opening, or may have started, and cancels an open one on the way out. During a checkout, the footer's policies and website open in a new tab, so the guest can read the terms they accept without leaving. If the page goes within the site anyway, it releases the checkout with a request that outlives the page (`keepalive`), and every answer that arrives after the page has gone is dropped. Leaving the site any other way, such as closing the tab or typing another address, releases nothing: the seats stay held until the checkout expires, up to 15 minutes after it opened.

## Waiver signing (G2.15)

The waiver flow in the [waiver contract](../../packages/domain-waivers/README.md), built phone first.

- **`/waiver`, from the request email.** The link is `/waiver#t=<token>`. The page takes the token out of the address at once (`history.replaceState`) and keeps it in memory, then shows a start screen naming nothing personal. Only the guest's tap sends the token, in the body of `POST /v1/public/waiver-sessions`, so a mail scanner's GET or a link preview consumes nothing. The answer is a signing session for one participant's waiver, for the participant or, for a minor, the guardian the booking names.
- **Review and sign.** The waiver's full text, each acknowledgment to check, confirmation of who is signing, a guardian's relationship (parent or legal guardian), consent to sign electronically, and the typed signature, with the name the booking gives the signer as its hint. Sign is the one primary action. A refusal comes back by field and marks each field; a changed waiver, a superseded one, one signed through another link, and an ended session each have a designed screen that says what to do, with the operator's contact. A link or a reloaded session whose waiver was signed, replaced, or is no longer needed says so, not only that the session ended. Too many tries or a server failure keeps the start screen's token, or the filled form, for another tap.
- **Signed.** The record of what was signed and "Download your signed copy", the PDF exactly as stored.
- **Secrets.** The link's token is never stored. The session's secret travels only as `Authorization: Bearer` and lives in sessionStorage under one key (`tidegrid.waiver.session`, in `src/waiver/session.ts`), so a reload keeps the open waiver; it belongs to the tab, ends with it, is cleared when the session ends or expires, and is replaced when another link opens. No name, address, or signature is stored, and no address carries a token or personal data.
- **The party's waivers on `/manage`.** `PartyWaivers` (`src/waiver/PartyWaivers.tsx`), placed by one insertion in lane 1's management page after "Who's coming", reads `GET /v1/public/manage/waivers` with lane 1's booking session as the bearer. Each named person has a status as an icon and a label (Signed, Waiting for signature, Email didn't go through, Needs an email address, Email on hold, Not sent yet), where the latest email went (masked), and what the booker can do. An email a sending limit holds says when it goes out ("We'll email the link to … at 6:12 PM"), or, when a cap holds it with no time, that the operator can send it once the limits allow. It reads again after each party edit and when the tab comes back into view, so a signature made in another tab shows. It shows nothing when no waiver applies or the booking is canceled, and never offers the signed PDF: the booker named the party but signs only for themselves.

## The management page (G2.11c)

Lane 1 of wave 2: the booking after it confirms, opened without an account. The API is in the [booking contract](../../packages/domain-booking/README.md#guest-self-service-lane-1-g211c).

1. **Opening.** The confirmation email's button opens `/manage#t=<token>`. The page takes the token from the fragment, removes it from the address and the tab's history at once, and asks "Open my booking": only that click sends the token, in a POST body, so an email scanner or a link preview opens nothing. A used, expired, replaced, or revoked link has its own screen and offers a new link by email to the booker on file. Right after paying, the confirmation's "Name your party now" opens the same page with the checkout's secret, within an hour, without waiting for the email. A link opened in the same tab, which changes only the fragment, is taken the same way.
2. **The booking.** Its trip, where to meet, the booker, the receipt as a ledger (a free line says "at no charge"), and what canceling now gives.
3. **Who's coming.** One place per seat. The guest names each place and corrects it in place; a guest under 18 needs a parent or guardian's name and email. One place is edited at a time, its Save is the page's only primary action while it is open, and focus returns to its row when it closes. A retry after no answer sends the same request under the same key.
4. **Canceling.** The amount comes first ("If you cancel now: You get a full refund of $130.55."), with when it changes. Cancel booking asks again in a dialog whose default is Keep my booking, and the command carries the amount shown: if the terms changed meanwhile, the page shows the new amount and asks again. Afterwards focus moves to what happened, and the page shows the refund's state.
5. **Coming back later.** Email me a new link, and Close my booking on this device, which ends the session.

With `VITE_DEMO_MAILBOX=1` the confirmation and the management page link to the API's local mailbox (`src/manage/DemoMailbox.tsx`); production builds leave it out.

## Secrets and personal data

- **The booker's name and email** live in the page's memory and travel only in the body of `POST /v1/public/checkout-sessions`. They are never in an address, a log, analytics, or storage.
- **The checkout secret** (43 base64url characters from `crypto.getRandomValues`) and **the payment's client secret** are capabilities. They travel only in `Authorization: Bearer` headers and live in memory.
- **sessionStorage, two records**, both in `src/booking/resume.ts`:
  - **The open checkout.** While a checkout is open, its id, its quote id, the checkout secret, whether a payment was sent or tried, and the clock offset, under one key, so a reload can follow a payment that was already sent instead of leaving the guest without an outcome. It is justified because the alternative, a reload after paying, would leave a guest who paid with no booking reference until email arrives (G2.16). It is scoped and short-lived: sessionStorage belongs to the tab, is never sent anywhere, and is gone when the tab closes; one record for one checkout, which a new checkout replaces; cleared when the checkout reaches any final state, is canceled, or is read more than 10 minutes past its expiry on the server's clock, as the record learned it. Never the name, the email, or the client secret. A reloaded page therefore cannot pay: before payment it offers to start over, releasing the held seats first.
  - **The last confirmation.** What the confirmation screen said: the booking reference, the trip, the place, the party, the extras, and the total. No secret, no name, no email. It exists because the confirmation email may not have arrived yet (and on deployed environments the email shim sends none), so a reload of the confirmation would otherwise lose the reference; the console's booking list (G2.12b) helps the operator, not the guest. The next confirmation in the tab replaces it, a new checkout for the same trip removes it (so a reload never shows an earlier booking for a later checkout), and it goes when the tab closes.
- **The management link's token** arrives in the URL's fragment, which the browser never sends to a server, and is removed from the address and the tab's history before any request. It stays in memory until the guest asks to open the booking, and travels only in that POST's body.
- **sessionStorage, a third record**, in `src/manage/session.ts`: the booking session's token, its expiry, and the reference, so a reload keeps the guest in for the session's hour. It also keeps the used link's token, which opens nothing but can ask for a new link to the booker's own address. One record for the tab, which another booking replaces; gone when the tab closes, the session ends, or the API says it has. The session token travels only as `Authorization: Bearer`.
- **The address** carries only the trip, the party (`t.<code>`, `guests`, `a.<code>`), the step, and on the details step the quote id, which is not authority and holds no personal data. Never a secret, the promotion code, the booker, or the checkout's id.
- A reload during a checkout whose own hold took the trip off sale (a charter's whole boat, or the last seats) reads the trip from the checkout's quote, since the offer then answers 409.

## Content security policy

`public/_headers` keeps the guest policy strict: no inline script or style (React and the design system set styles only through the CSSOM), and zod in jitless mode (`src/zod-jitless.ts`), so parsing a contract never compiles code. `connect-src` names the API origin, `https://cloudflareinsights.com` for Cloudflare Web Analytics' manually added beacon, and `'self'`, because the automatically injected beacon reports to the site's own `/cdn-cgi/rum` ([Cloudflare's Web Analytics FAQ](https://developers.cloudflare.com/web-analytics/faq/)). The page's own code fetches only from the API. `src/static.test.ts` and `src/zod-jitless.test.ts` hold these.

## The installable site (G2.14b)

The site is still one assets-only SPA for every operator. An edge Worker (`worker/index.ts`) runs first only for `/manifest.webmanifest`, `/icons/*`, and `/sw.js` (`run_worker_first` in `wrangler.jsonc`). It reads the tenant from the request URL's hostname only, never from a header, and asks the API's `GuestGateway` entrypoint over a service binding; the gateway checks the host with the strict origin rules itself.

- **Manifest.** The operator's own: its name, a `short_name` cut to 12 characters, `theme_color` from its primary, the neutral page background, `start_url`, `scope`, and `id` at `/`, standalone display, and two SVG icons. `Cache-Control: no-cache` and an ETag from the slug and brand version. There is no default tenant and no generic manifest.
- **Icons.** A square of the brand's primary with its validated SVG mark centered, checked again by the logo validator, or a neutral mark for no logo, a lockup, or a raster mark (D3(a)). Served under `default-src 'none'; style-src 'unsafe-inline'` with nosniff. No apple-touch-icon.
- **Service worker.** Vite builds `src/sw/sw.ts` into an unhashed classic `/sw.js` with this build's hashed `/assets/*.js` and `*.css` injected as the precache. It precaches those and one neutral offline page (`neutral-offline.html`, under a fixed key), caches fonts as they arrive, and never caches a navigation, a cross-origin request (the API), a non-GET, or anything with `Authorization`: a navigation's URL keeps its `#t=` token. Navigations go network first and fall back to the offline page. The page registers it at `/` with `updateViaCache: "none"` once its operator is ready (`src/sw/register.ts`, from the bootstrap). Update policy (D11(a)): a new version installs and waits. The next page load finds it waiting and posts `SKIP_WAITING`, once per page load ("Try again" never asks again), and the worker takes over only when that page is the site's one open window (it looks a few times over about seven seconds, since a window that just closed can stay on the browser's client list for a moment). With another tab or the installed app open it keeps waiting, because taking over would switch every open window at once and its activation deletes the old build's cache. `scripts/check-precache.mjs` fails every build whose precache names a file the build did not write.
- **Kill switch, two layers, only on a definite miss.** When the bootstrap reads `tenant_not_found`, the page unregisters every worker and deletes every cache. For a host the gateway reports as a miss, the Worker serves `src/sw/kill-switch.ts` as `/sw.js`, with `Clear-Site-Data: "cache"`; it deletes caches and unregisters, and never touches storage, where an open checkout and a manage or waiver session live. A gateway error, a timeout, or a withheld brand is 503 with no-store and clears nothing. `GUEST_SW_KILL_SWITCH=1` builds the kill switch for every host: the rollback for a bad service worker.
- **Headers.** The page's policy adds `worker-src 'self'` and `manifest-src 'self'`. Responses the Worker writes set their own security headers, because `public/_headers` covers assets only.
- **Preview hostnames.** `wrangler.jsonc` lists one Workers Custom Domain per synthetic tenant, `<slug>.book.tidegrid.us` (D8(a)); a test keeps it equal to `config/tenants`. It is not deployed until G2.14b-live; named environments have no routes.

## API follow-ups

Found while building the checkout, ranked by the code review. None blocks the demo; the page works around each one. The API is unchanged here; each is a proposal for the goal that owns the API.

1. **A Bearer-authorized read of the payment's client secret** while a checkout is open, with the checkout secret. Today a reload cannot pay, and a lost answer to opening a checkout can be recovered only by resending the same body, which needs the booker's details in memory.
2. **Structured 422 problems**, such as `problems: [{ code, subject }]`. Today the page parses the problem codes and their subjects out of the message text, and falls back to the error's code.
3. **The offer answering 409 because of the guest's own hold.** When a checkout's own hold takes the last seats or the whole boat, the offer refuses the trip, so a reload shows the checkout from its quote instead.
4. **A `remaining` field** on a capacity refusal. A quote's 409 `insufficient_capacity` gives no count, and a checkout's gives it only in the message.

## Local development

```sh
cp .env.example .env.local      # VITE_API_BASE, the local API origin
GUEST_DEV_PORT=5233 pnpm dev    # http://<slug>.book.localhost:5233
```

The seed must run with `SEED_LOCAL_HOSTNAMES=1`. The API's `dev` environment accepts any seeded `*.book.localhost` origin (`PUBLIC_CORS=dynamic`); the fake payment provider's routes follow the same rule. Payments need `PAYMENT_PROVIDER=fake` and a `FAKE_PAYMENT_WEBHOOK_SECRET` in the API's `.dev.vars`. Email links point at `GUEST_LINK_ORIGIN` in the API's `.dev.vars` (`http://{slug}.book.localhost:<port>`); `VITE_DEMO_MAILBOX=1` adds the links to the local mailbox.

The guest Worker, on the built site (no Vite), on port 5361:

```sh
VITE_API_BASE=http://localhost:8961 GUEST_LOCAL_API=http://localhost:8961 pnpm build
pnpm dev:stub     # a stub GuestGateway with the two synthetic brands, no database
pnpm dev:worker   # bound to the API's GuestGateway: run the API with `wrangler dev --env dev --port 8961`
```

Both serve the built `dist/`, so build first; a later `pnpm build` (a `pnpm check` runs one in `release:dry`) replaces it. `/offline` renders neutral, without the operator's header and footer.

`GUEST_LOCAL_API` adds the local API to `connect-src` in the built `dist/_headers` only (`scripts/local-headers.mjs`); the committed `public/_headers` and its test stay unchanged.

## Tests

`pnpm --filter @tidegrid/guest-site test`. The checkout's tests run the page in jsdom against a fake API (`src/booking/fixtures.ts`) with the guest in Tokyo and the marina in New York. They cover each step and state, the keys and their reuse, polling to every outcome, a reload at each step, Back and Forward, leaving an open checkout, a device clock that is off, and that no secret or personal data reaches an address. The management page's tests (`src/manage/*.test.ts(x)`, with `src/manage/fixtures.ts`) cover opening from a link and from the checkout, each link problem, a reload, naming the party with its keys and retries, every remedy and changed terms when canceling, ending the session, and that no token or guest detail reaches an address. `src/design-system-dom.test.tsx` covers the design system's behavior that needs a DOM.

The guest Worker's tests run in workerd with stub bindings and no `dist/` (`vitest.workers.config.ts`, `worker/*.test.ts`), and the service worker's in Node against a fake scope (`src/sw/sw.test.ts`). The browser checks are Playwright (`playwright.config.ts`, `e2e/`), at 375 and 1280: `pnpm e2e` runs part A against the stub gateway, and `E2E_MODE=full` runs part B against the API and a seeded PostgreSQL 17, as the CI browser job does. Locally, `E2E_CHANNEL=chrome` uses an installed Google Chrome; never run `playwright install` on the owner's machine.
