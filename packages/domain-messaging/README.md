# @tidegrid/domain-messaging

Transactional email for the demo build: a provider-neutral email adapter, a fake provider, a Cloudflare Email Service adapter that is built but switched off (G2.16a), branded templates, and outbox-driven delivery (the G2.16 demo shim, lane 1). The design authority is [product scope: transactional email](../../docs/v2/02-product-scope.md#transactional-email-sms-and-replies), [the target architecture](../../docs/v2/04-architecture.md#messaging) (provider-neutral adapter, versioned templates, recorded delivery outcome) and its [retained invariants](../../docs/v2/04-architecture.md#retained-invariants) (domain state and outbox records commit together; external calls never hold a database lock). Tables are in migration `0009_self_service_and_email.sql` and follow the [tenancy contract](../database/README.md).

## The email shim is the demo's email

The owner decided on 2026-10-05, "You can just shim stripe or others". The demo therefore sends email through a fake provider behind this adapter, as payments run through the payment shim, and does not wait on Cloudflare Email Service. The narrowing is recorded in the [demo build plan](../../docs/v2/12-demo-build-plan.md#goal-sequence) beside the payment narrowing. The fake follows the path a real provider will: TideGrid enqueues a message in the transaction that causes it, a delivery job sends it after commit with an idempotency key, and the outcome is recorded. The Cloudflare Email Service adapter (G2.16a, [below](#the-cloudflare-adapter-g216a)) is built behind the same interface and stays off in every deployed configuration until the owner authorizes the live step. The API accepts the fake only in local development (coordinator default D6 A, 2026-10-28, confirmed by the owner on 2026-11-08; the fake itself still refuses only `ENVIRONMENT=production`). No real email is delivered.

## Enqueueing a message

```ts
enqueueMessage(trx, ctx, {
  dedupeKey,          // "<topic>:<ids>", e.g. "booking.confirmation:<bookingId>"
  template,           // "booking_confirmation", "waiver_request", ...
  templateVersion,    // the template's version, recorded with the message
  to: { email, name? },
  bookingId?, participantId?, subjectRef?,   // what the message is about
  content: { subject, preview?, blocks: EmailBlock[] },
  accessLink?: { purpose, path, ttlSeconds? }, // a link issued at send time, see below
  notBefore?,         // send no earlier than this (a reminder); default now
}): Promise<{ kind: "enqueued"; messageId } | { kind: "duplicate"; messageId }>
```

- **In the caller's transaction.** The message row commits or rolls back with the change that causes it: a booking's confirmation, its cancellation, a participant's waiver request. Nothing is sent inside a transaction.
- **Once per key.** `dedupeKey` is unique per tenant, for ever. A retried command, a replayed webhook, or a hook that runs twice enqueues nothing new and answers `duplicate` with the first message's id. Choose keys that name the logical message: one confirmation per booking, one waiver request per assignment and delivery generation.
- **Staff resends commit with their ledger row.** A message whose key starts `booking.resend:` commits only beside its row in `booking_email_resends`, written in the same transaction (a deferred check, migration 0014), and its insert first takes the tenant's resend lock; enqueue one only through the booking module's `resendBookingEmail`.
- **Rendered now, branded.** The content is rendered when it is enqueued, into the tenant's branded HTML and plain text, with the tenant's active brand (its name, colors, and contact email as the reply-to address). The footer names the operator's contact email and phone, a North American number written as the booking site writes it, (305) 555-0142 (`displayPhone` in `src/render.ts`). The rendered subject and bodies are stored with the template version, so what was sent is what the record says. Callers give structured blocks, never markup: every text is escaped, so tenant and guest content cannot inject HTML.
- **Personal data.** The recipient, the rendered bodies, and the names in them are personal data. They stay in the message row and the provider call. Audit rows and events carry ids only.

```ts
type EmailBlock =
  | { kind: "heading"; text: string }
  | { kind: "paragraph"; text: string }
  | { kind: "details"; rows: { label: string; value: string }[] }        // a label and value table
  | { kind: "lines"; rows: { label: string; amount: string; strong?: boolean }[] }  // a receipt
  | { kind: "action"; label: string; href: "access_link" | `https://${string}` }   // the one button
  | { kind: "note"; text: string };
```

### Access links in email

A link that grants access (the booking's management link, and a waiver signing link for G2.15) is never stored in a message. The message names its purpose and path; the delivery job issues the link when it sends, stores only the token's SHA-256, and writes the URL into the body at that moment, in the action's `href` and as visible text. The raw token travels only in the email, in the URL's fragment (`https://<operator site><path>#t=<token>`), so it never reaches a server log, a `Referer` header, or a link scanner's GET. The guest page exchanges it for a restricted session with an explicit POST (the [booking contract](../domain-booking/README.md#guest-self-service-lane-1-g211c)).

- The link's origin is the operator's guest site, from `GUEST_LINK_ORIGIN` (default `https://{slug}.book.tidegrid.us`; locally `http://{slug}.book.localhost:<port>`), and the delivery job checks that its hostname is an active, verified hostname of the message's tenant before sending. A message whose link host does not resolve to its tenant fails as `link_host_unmapped`. Since G2.14b the origin goes through the same strict origin parser as a browser Origin, with the deployment environment the API passes (`environment`): https only, no port, no path, no trailing dot, and no `*.localhost` name outside local development. A caller that passes no environment gets the strict deployed rules; local tests on `*.localhost` say `environment: "local"`.
- The issued link keeps the message's booking, participant, and `subjectRef`, and the message's id.
- Issuing a link for a message revokes, as `superseded`, the unused links of the same booking, purpose, participant, and subject that older messages carried (written before it), so the newest email's link is the one that works. A retry of an older message never supersedes a newer message's link: a confirmation whose answer was lost, retried after the guest asked for a new link, leaves the new link working. Retries of one message revoke nothing of their own. On a provider that deduplicates (the fake), the idempotency key keeps the first accepted email, and a token issued for an attempt the provider never accepted is never delivered and expires. On one that does not (Cloudflare), an attempt whose outcome is unknown is never repeated (see Delivery), so a message's delivered copy holds its only link. Superseding skips a link another transaction holds at that moment (it is being used or revoked), so a claim never waits on a lock.
- Closing a subject's access closes its pending email too. `revokeAccessLinks` with `recipient_changed`, `completed`, `withdrawn`, or `booking_canceled` first takes the row locks of every link-carrying message of that booking, purpose, participant, and subject written before its transaction and not yet sent (queued or being sent), cancels them (`failureCode` `recipient_changed` or `access_withdrawn`), and only then revokes the links. Because it waits for a delivery claim in progress, the link that claim issued is revoked with the rest; a message no delivery has claimed yet, which has no link, is canceled before one is ever minted; and a claim that comes while the revocation is open skips the locked message. So no email goes to an address that was corrected away from, or asks to sign a waiver already signed, with a link that works. `staff` and `superseded` revocations close no email. Delivery checks again when it claims a message: one whose own link was revoked, or whose booking and purpose saw such a revocation after the message was written, is canceled. "Written" is the row's own insert time (`email_messages.written_at`, `0052`, stamped with `clock_timestamp()` by its trigger), not its transaction's start, so a command that waited behind a correction and wrote its email afterwards, to the new address, is delivered; rows from before `0052` use `created_at`.
- The claim keeps a backstop for links revoked some other way (an operator's statement, a future caller): before it issues a link, under the message's row lock, it cancels a message whose own link was revoked for any reason but `superseded`, or whose subject saw a link revoked as one of those four reasons after the message was written. That backstop sees only revocations committed before the claim began; the guarantee above is the one to rely on.

## Access links and guest sessions

Every function takes the caller's tenant transaction, so it commits or rolls back with the caller's change. Tokens are 32 random bytes, base64url (43 characters); only SHA-256 hashes with a purpose prefix are stored. Purposes are `booking_manage` (the booking's management page, lane 1), `waiver_sign` (a participant's waiver, G2.15, which needs a participant), and `participant_profile` (a participant's own details, from an invitation, W3-G2.11-rest, which also needs a participant). `revokeGuestSessions` can keep one session live (`exceptSessionId`), the one making a change.

```ts
redeemAccessLink(trx, ctx, { token, purpose }): Promise<
  | { kind: "redeemed"; link: { linkId, bookingId, participantId, messageId, subjectRef, purpose } }
  | { kind: "invalid" }    // malformed, unknown, another tenant's, or another purpose's
  | { kind: "expired" } | { kind: "used" }
  | { kind: "superseded" } // a newer email's link replaced it
  | { kind: "revoked"; reason: "completed" | "withdrawn" | "recipient_changed" | "booking_canceled" | "staff" }
>
revokeAccessLinks(trx, ctx, { bookingId, purpose, participantId?, subjectRef?, reason }): Promise<number>
openGuestSession(trx, ctx, { link, ttlSeconds? } | { checkout: { checkoutSessionId, bookingId }, ttlSeconds? }):
  Promise<{ sessionId, token, bookingId, participantId, purpose, subjectRef, expiresAt }>
resolveGuestSession(trx, tenantId, token, purpose): Promise<GuestSession | null>
revokeGuestSession(trx, ctx, sessionId): Promise<boolean>
revokeGuestSessions(trx, ctx, { bookingId, purpose, participantId?, subjectRef? }): Promise<number>
issueAccessLink(trx, ctx, { bookingId, participantId?, purpose, subjectRef?, messageId?, ttlSeconds }) // the delivery job's
```

- **Redeem only on an explicit POST.** A link is consumed once, atomically: concurrent redemptions of one token serialize on its row, one wins and the rest answer `used`. A page that receives a link reads the token from its URL fragment and redeems it only when the guest acts, so an email scanner's GET or a link preview consumes nothing.
- **Open the session in the same transaction.** The database opens a session only from a link consumed in that very transaction (`guest_sessions_evidence`), or, for the guest who just paid, from the checkout that made the booking within an hour of confirmation. A session lasts at most 12 hours (one hour by default) and returns its raw token once.
- **Revocation reasons.** `completed`: the purpose is done (a waiver signed). `withdrawn`: no longer needed (a participant or requirement removed). `recipient_changed`, `booking_canceled`, `staff`: as named. `superseded` is set by issuing a newer link. Without `participantId` or `subjectRef`, every participant's or subject's links of that booking and purpose are revoked; pass `null` to mean "the booking-level ones".
- **Times.** The database clock decides expiry. A link's or session's expiry can move earlier, never later, as holds' can; tests make time pass that way.

## Message status

```ts
cancelMessage(trx, ctx, messageId, options?: {
  linkReason?: AccessRevocationReason; // why its links stop working; withdrawn by default
  code?: string;                       // why it was canceled, such as recipient_changed
  revokeLinks?: boolean;               // false keeps its links working; true by default
}): Promise<
  | { kind: "canceled"; inFlight: boolean; revokedLinks: number }
  | { kind: "not_cancelable"; state } // already sent, failed, or canceled
  | { kind: "not_found" }>
getMessageStatus(trx, tenantId, messageId): Promise<MessageStatus | null>
listBookingMessages(trx, tenantId, bookingId): Promise<MessageStatus[]>

interface MessageStatus {
  id; template; templateVersion;
  state: "queued" | "sending" | "sent" | "failed" | "canceled";
  attempts; lastAttemptAt; nextAttemptAt; sentAt; failedAt; canceledAt;
  failureCode;   // the last attempt's error: provider_unavailable, bounced, retries_exhausted, link_host_unmapped, send_error, deadline_reached,
                 // and from the Cloudflare adapter outcome_unknown, delivery_failed, invalid_message, recipient_suppressed, recipient_not_allowed,
                 // provider_rate_limited, provider_quota_exceeded, sender_not_verified, provider_account_suspended; null once sent;
                 // for a canceled message, the cancellation's own reason (recipient_changed, access_withdrawn, booking_canceled,
                 // resent: a newer email replaced it) or null; the contract's MESSAGE_FAILURE_CODES lists them all
  provider;
  staffResend;   // true for a booking email staff sent again (G2.16b): its dedupe key starts STAFF_RESEND_TOPIC, "booking.resend:"
  createdAt;
}
```

`staffResend` is computed from the dedupe key in the read; there is no column. Clients keep words for each code in `MESSAGE_FAILURE_CODES` (packages/contracts) and show any other code generically.

`cancelMessage` cancels a message that has not gone out, queued or being sent, and in the same transaction revokes the unused links it carried (with `linkReason`). Once the caller commits, no email of that message opens anything and the delivery job never claims it again. It waits for a delivery claim in progress, so the link that claim issued is revoked too; the claim is a short transaction that never waits on another's lock. A message canceled mid-send (`inFlight: true`) may still arrive, with a link that opens nothing; its attempt records nothing and is never retried. Correcting an address: in one transaction, revoke the old address's links as `recipient_changed` (which closes the old address's pending email, as above), and enqueue the new one. Calling `cancelMessage` on the old message as well is harmless: it answers `not_cancelable` with state `canceled`. A message with no link, which no revocation reaches, is canceled with `cancelMessage` alone.

**Locks for callers.** A transaction that may call `cancelMessage` or `revokeAccessLinks` must not hold `FOR UPDATE` on a row a link references (the booking, the participant): the claim's foreign key checks take `KEY SHARE` on them, and would wait while those functions wait for the claim. Lock those rows `FOR NO KEY UPDATE`, as domain-booking does.

Status reads carry no recipient or content. Provider acceptance is not proof that a guest read a message or used its link.

## Email exceptions (W1-EMAIL-EXC)

```ts
listEmailExceptions(trx, tenantId, { limit: 1..100; before?: messageId }): Promise<
  | { kind: "page"; exceptions: EmailExceptionView[]; nextBefore: string | null }
  | { kind: "cursor_invalid" }>

interface EmailExceptionView {
  id; template;
  kind: "booking" | "waiver";                               // waiver_* templates are waiver
  state: "failed" | "outcome_unknown" | "delivery_failed";  // by the last error code
  attempts; failureCode; failedAt; staffResend;
  laterSent;  // a later message of the same template, booking, participant, and subject was sent
  booking: { id; reference; timeZone } | null;              // the trip's zone, for times
}
```

The tenant-wide read behind the console's email exceptions list (`src/exceptions.ts`), a follow-up to G2.16b D9 A. It lists every message of one tenant in the `failed` state, newest first by `failed_at`, then by id, a page at a time. `state` splits `failed` by the last error: `outcome_unknown` and `delivery_failed` are their own states, and every other code is `failed`. No new message state exists. `before` is the last id of the previous page; one that is malformed, unknown, another tenant's, or names a message that is not failed answers `cursor_invalid`. A failed message never changes again (the 0009 trigger), so a cursor keeps naming the same place.

- **Tenancy.** The caller runs it in `inTenantTransaction`, so row-level security limits every table to the tenant, and the query also filters each one by `tenant_id`. Under another tenant's transaction, a tenant's id lists nothing, and its message ids are `cursor_invalid`.
- **No personal data.** It selects no recipient, name, subject, or body: only the template, the delivery facts, and the booking's id, reference, and trip zone.
- **Who calls it.** `GET /v1/staff/tenants/{tenantId}/email-exceptions` in `apps/api-worker/src/routes/booking-email-staff.ts`, for roles that hold `bookings.read` (owners and booking staff, D2). Finance is refused there (403). The contract is `packages/contracts/src/email-exceptions.ts`.
- **No index (D3).** At demo size the tenant's messages are read in full; the `laterSent` check uses `email_messages_booking_idx`. An index on `email_messages` waits for the `CREATE INDEX CONCURRENTLY` runner (rule R4) and a measured need.
- **Coordinator defaults, pending owner confirmation.** D1: waiver requests are included, labeled by kind. D2: owners and booking staff only. D3: no index.

Tests: `src/exceptions.test.ts` (the state and kind rules and the guards) and `src/exceptions.integration.test.ts` (the order, paging, cursors, and two tenants under row-level security).

## Delivery

A delivery job sends due messages after commit and records each outcome. It runs from the API Worker's cron, after the checkout sweep, and right after a request commits a message (in the background, so the guest sees the email at once). Correctness never waits for it.

- **States, one way.** `queued`, then `sending` (claimed for a short lease), then `sent`, or back to `queued` with a later attempt after a temporary failure, or `failed`. A queued or sending message may be `canceled` (a waiver request made obsolete, an address corrected); a sending one's attempt then records nothing. The database refuses every other move, for every role.
- **Idempotency is the provider's to state.** The provider receives the message id as its idempotency key, and says in `deduplicates` whether a repeat returns the first email. Only `true` counts: a provider that leaves it unset is treated as one that does not, so a new provider fails safe. A crash after the provider accepted a message and before the outcome was recorded leaves the message `sending` until its lease lapses. Then:
  - **A provider that deduplicates** (the fake): the job claims it again and sends with the same key, and the provider answers with the first message instead of sending twice. An unknown outcome is retried the same way.
  - **A provider that does not** (Cloudflare, `deduplicates: false`): at most once (coordinator default D1 B, 2026-10-28, confirmed by the owner on 2026-11-08). The lapsed message fails as `outcome_unknown` with no second send. So does an attempt whose outcome is unknown: an `EmailProviderUnavailableError` with `outcome: "unknown"` (the default), or a throw that is not the provider's answer once the provider was called. A throw before the call (filling the link into the bodies) sent nothing, so it retries as `send_error` on every provider. Only a temporary failure the provider says was not sent (`outcome: "not_sent"`) is retried. This keeps product scope's rule that a retry never sends the same message twice through one channel. The cost is a missed email: a guest recovers a management link by asking for a new one, a waiver request has its audited resend, and the confirmation and the cancellation notice have staff resend from the console (G2.16b, built; see the [booking README](../domain-booking/README.md#staff-resend-of-a-bookings-email-g216b)). A staff resend is a new message with its own key, never a second send of the lost one.
- **Account-level faults stop the run.** An `EmailProviderUnavailableError` with `scope: "account"` (a sender not verified, a suspended account, a daily limit) is retried for its message, and stops the tenant's run and the sweep (D2 B): every other email would meet it too. When the provider said it took nothing and the code is one of `ACCOUNT_FAULT_CODES`, the retry gives its attempt back and waits `ACCOUNT_FAULT_RETRY_SECONDS` (600 s), so an outage never exhausts an email (migration 0015, owner decision 2026-11-07). A rate limit is not one: Cloudflare limits per account, domain, and recipient under one code, so a rate-limited message retries on its own and the run goes on.
- **A deadline.** `deadline` (epoch ms) claims a message only while the provider's `sendTimeoutMs` and a 2 s margin still fit before it. After-commit delivery passes 18 s from the moment its connection is ready, capped by the request's start plus the 30 s `waitUntil` budget (since 2026-11-07), and leaves the rest to the cron. After each claim delivery checks again, and calls the provider only while a whole send and the 2 s margin that records it still fit; otherwise the claim is a counted retry, `deadline_reached`, and the run stops. The cron passes none of its own, but the sweep now derives one from its budget: the run's start plus `budgetMs` (20 s), or the caller's deadline if earlier (pre-pilot hardening item 5, D9 B, a coordinator default confirmed by the owner on 2026-11-08). A run's sends therefore end within its budget, so the email job no longer delays the hostname job behind it on the cron's one connection by up to 25 sends of 10 s a tenant. A scheduled handler may run for 15 minutes of wall time ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)); the budget, not that limit, bounds the job.
- **Fair turns across tenants (Part C).** `app.email_delivery_tenants` names due tenants least recently served first, from the `sweep_turns` stamps of migration 0013, and `runFairSweep` (database package) gives each listed tenant a turn of up to five messages (`turnMessages`), stamping it first, then goes round the tenants whose turn was full until the budget runs out. `limit` (25) stays the cap for one tenant's run. Turns start only while a claim still fits before the deadline (`sweepWindow`): with a 20 s budget and Cloudflare's 10 s send bound plus the 2 s margin, that is the first 8 s, so a tenant is never stamped or counted for a turn that could send nothing. A tenant's link origin is read once a run, at its first turn. An account-level fault or the deadline ends the whole run, as before. The report adds `turns`, `passes`, `deferredTenants`, and `stampFailures`.
- **Reading a stop in the cron log (hardening Part E, D-E5 B, a coordinator default of 2026-10-29, confirmed by the owner on 2026-11-08).** The cron logs `tidegrid.email_sweep.account_fault` on every summary, with `deferred_tenant_count` and the other counts. A deadline stop and a spent budget are one condition: the claim window closed (`sweepWindow` ends the turns where the claim check stops claiming, with the same reserve), inside a turn or between turns, and the log does not tell those apart. So `account_fault: true` means the provider refused for the account, the run stopped, and the tenants after it are deferred. `account_fault: false` with `complete: false` and deferred tenants means the window closed. `account_fault: false` with `complete: false` and no deferred tenant means a tenant still had mail, a tenant failed, the list hit `tenantLimit` (100), a turn asked for more with nothing done, or the window closed inside the last listed tenant's turn. A failed stamp logs as `email_sweep_stamp_failed`, never as a tenant failure.
- **Retries.** A temporary failure (`EmailProviderUnavailableError`) retries after 1, 5, 15, and 60 minutes, then 4 hours, and fails after six counted attempts as `retries_exhausted`; an account-level fault's attempt does not count (above). A refusal (`EmailProviderRejectedError`, such as a bounced address) fails at once with the provider's code. Failures stay visible on the message and in staff reads.
- **No duplicate claims.** Claims take due rows with `FOR UPDATE SKIP LOCKED`, so concurrent jobs never send one message at once; recording an outcome checks that the attempt it ran is still the message's latest.

## The adapter

```ts
interface EmailProvider {
  name: "fake" | "cloudflare";
  deduplicates?: boolean;   // only true promises a repeat with the same key returns the first email; unset means it does not
  sendTimeoutMs?: number;   // the longest one send can take, when the provider bounds it
  send(message: {
    idempotencyKey, tenantId,
    from: { email, name }, replyTo, to: { email, name },
    subject, html, text,
  }): Promise<{ providerMessageId: string }>;   // throws EmailProviderUnavailableError or EmailProviderRejectedError
}
new EmailProviderUnavailableError(code?, message?, { outcome?: "not_sent" | "unknown", scope?: "message" | "account" })
```

No method runs inside a database transaction. `tenantId` is metadata, as a provider tag would be; the fake files messages by it.

## The fake provider

`FakeEmailProvider` keeps what it "sends" in its own append-only, tenant-owned table, `fake_email_deliveries`, and never reads or writes TideGrid's message table.

- **Exists only under `EMAIL_PROVIDER=fake`,** and refuses `ENVIRONMENT=production`. The API builds it only when `ENVIRONMENT=local` and no `EMAIL` binding is set: it stores full bodies, raw link tokens included, so it must never run on a deployed database.
- **Idempotent by key.** The first accepted delivery for a key is the only one; a repeat answers with it.
- **Scripted failures for the demo.** A recipient whose local part ends in `+fail-once` gets one temporary failure per message before it is accepted; one ending in `+bounce` is refused as `bounced`. Everything else is accepted.
- **The mailbox.** With `EMAIL_PROVIDER=fake` and `ENVIRONMENT=local` only, the API serves a mailbox at `/v1/fake-email/mailbox`: each local guest site's accepted messages, newest first, and each message's HTML, so the demo can open the management link. Elsewhere the routes answer 404.

## The Cloudflare adapter (G2.16a)

`createCloudflareEmailProvider({ binding, recipients, environment, timeoutMs?, log? })` sends through the Workers `send_email` binding with the structured builder ([Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/)). It holds no secret and makes no `fetch` call: the binding is authorized by the account and the Worker's deploy. It is switched off in every deployed configuration (see the API Worker's `src/email.ts`).

- **Mapping.** `from` as `{ email, name }`, the name being the operator's name and " via TideGrid" ([sender identity](#sender-identity-w1-sender-guard)); `to` as `{ email, name }`, or the bare address when there is no name; `replyTo` only when set; both bodies. Two headers only: `X-TideGrid-Message-Id` (the message id, opaque, for correlation; D5 A) and `Auto-Submitted: auto-generated`. The tenant id is never sent. `From`, `To`, `Subject` and `Reply-To` never go as headers ([headers](https://developers.cloudflare.com/email-service/reference/headers/)).
- **Not idempotent.** Cloudflare documents no idempotency key and sets `Message-ID` itself, so the adapter says `deduplicates: false` and delivery is at most once (see Delivery).
- **A recipient fence.** `recipients` is required: `{ kind: "only", addresses }`, compared lowercased and trimmed, or `{ kind: "any" }`, which the constructor refuses outside `environment: "production"`. A recipient off the list fails as `recipient_not_allowed` with no provider call. The API passes the `EMAIL_ALLOWED_RECIPIENTS` secret's addresses, so no address enters the repository (D3 B). At switch-on, queued mail to synthetic `.test` addresses fails the same way and never reaches Cloudflare (D4 A).
- **Bounded.** Each send races `timeoutMs` (the API passes 10 s). A timeout is an unknown outcome. Handlers go on the call before the race: a rejection after the timeout is swallowed and logged as `email_send_late_reject` with its documented code only; an acceptance after it is logged as `email_send_late_accept` with the message id and the provider id normalized as it would have been stored, the join key for a future events consumer. That copy went out, but its message ends `outcome_unknown` with no stored provider id.
- **Errors.** All 21 documented codes are mapped by name in `src/cloudflare-errors.ts`. This is TideGrid policy, since Cloudflare does not say which are retryable. Validation and header codes fail as `invalid_message`; `E_RECIPIENT_SUPPRESSED` as `recipient_suppressed`; `E_RECIPIENT_NOT_ALLOWED` as `recipient_not_allowed`; `E_DELIVERY_FAILED` as `delivery_failed`. A rate limit (`provider_rate_limited`) is known not sent and retries its message. A daily limit, an unverified or unavailable sender, and a suspended account are temporary account-level faults (`provider_quota_exceeded`, `sender_not_verified`, `provider_account_suspended`), known not sent. `E_INTERNAL_SERVER_ERROR`, an unknown code, a throw without a code, and a timeout are unknown outcomes (`provider_unavailable`, `outcome: "unknown"`), so they end `outcome_unknown`. The page gives `E_DELIVERY_FAILED` the description "Could not deliver the email" and the common causes "SMTP delivery failure, recipient server rejection". By the owner's decision of 2026-11-07 it is a definite failure with the neutral code `delivery_failed`: it fails at once and is never sent again, as before, and it does not claim the recipient's server refused it. A late `E_DELIVERY_FAILED`, after the timeout answered, is still an unknown outcome.
- **Fields checked first.** A control character (C0, C1, or DEL, so CR and LF too) in a display name or the subject, or a sender, recipient, or reply-to that is not one address, fails as `invalid_message` with no provider call. This does not lean on the message table's CHECKs, since the adapter is exported.
- **No personal data.** A provider error's message is never read and never becomes a `cause`; port errors carry TideGrid's code. Log lines carry event names, documented codes, the message id, hashes and flags (`tidegrid.email.*`), never an address, a name, a subject or a body.
- **Provider ids.** An id that fits `email_messages.provider_message_id` is kept. Anything else is stored as `cfh_` and the first 40 hex characters of its SHA-256 (`normalizeCloudflareMessageId`), and logged as normalized. An acceptance with no id is stored as `cf_no_id.<message id>`. The adapter never throws once Cloudflare accepted.
- **Tests.** A recorded-shape fixture (`src/cloudflare-fixture.ts`, not exported) stands in for the binding, built from the public docs: the header allowlist and `X-` rule, the API-field and platform headers, `allowed_sender_addresses`, 50 recipients, 5 MiB, 16 KB of headers, 998-character subjects, every documented code, a hang, a late answer either way, and odd ids. Its errors carry the recipient, names, subject and tenant id, so the no-leak tests test something. `src/provider.contract.ts` runs over it and over the fake (`src/fake.contract.integration.test.ts`).

### Known gaps

- **The adapter has never called the real service.** The result and error shapes, the `messageId` format, the code for a sender outside `allowed_sender_addresses`, and the error wording are unverified against live Cloudflare. G2.16-live settles them with a first authorized send to an owner inbox. The fixture answers ids in the shape of the [event-subscriptions](https://developers.cloudflare.com/email-service/reference/event-subscriptions/) examples (`0101018f7d0c4d9a-msg-deadbeef`); the headers page says `Message-ID` is generated on a Cloudflare domain, and the local simulation answers `<36 alphanumerics@sender domain>`. G2.16-live compares the id `send()` returns with `payload.messageId` on a delivered event before the join rule is settled.
- **`sent` means accepted.** Bounces and complaints after acceptance are not ingested, so they stay invisible to staff. That is a Core live gate blocker under "silent message failure" ([product scope](../../docs/v2/02-product-scope.md)), not only a follow-up. The proposed follow-up consumer of Cloudflare's Email Sending event subscriptions needs four things. A forward-only migration adding a unique index on `(provider, provider_message_id)`; only a CHECK exists today. An `app`-schema resolver such as `app.resolve_email_message(provider, id)`, because events arrive without a tenant and no RLS bypass is allowed. The adapter's normalization, applied before joining. The canonical inbox, deduplicating by event id and refusing events from another account or sending domain ([event subscriptions](https://developers.cloudflare.com/email-service/reference/event-subscriptions/)). Update, 2026-11-08: a local consumer is built (W1-EMAIL-EVENTS, [below](#email-events-w1-email-events)); it is not connected to the live event subscription yet.
- **Suppression crosses tenants.** Cloudflare suppresses an address per account or sending domain ([suppressions](https://developers.cloudflare.com/email-service/concepts/suppressions/)), and every tenant sends from the same TideGrid domain. A hard bounce or complaint on one operator's mail makes another operator's mail to that address fail as `recipient_suppressed`. Console wording stays neutral ("The provider will not deliver to this address"). Revisit with per-operator sending domains at the pilot gate. A soft-bounce suppression lasts 24 hours, longer than the retry budget, so such mail fails at once and staff resend is the recovery. Update, 2026-11-08: per-operator sending domains and TideGrid's own per-operator suppression are built (W3-G2.16-rest, [below](#sender-domains-and-suppression-w3-g216-rest)); an operator still shares Cloudflare's suppression with every operator on the shared sender until its own domain is verified.
- **Provider revalidation.** Stage 0 must choose an email provider that supports US customer data, deletion, export and audit ([build, hosting and operations](../../docs/v2/08-build-hosting-and-operations.md)). Cloudflare keeps recipient addresses in its suppression list and Activity log. Update, 2026-11-08: revalidated from Cloudflare's documentation ([below](#provider-revalidation-w3-g216-rest)).
- **Sender identity.** The display name was the brand name and the reply-to the brand's contact email, sent from the shared TideGrid sender, and a guard was needed before any production configuration. Update, 2026-11-08: the guard is built (W1-SENDER-GUARD, [below](#sender-identity-w1-sender-guard)). The reply-to is still the brand's contact email and is not verified; the guard only refuses one on a TideGrid domain.

## Sender identity (W1-SENDER-GUARD)

Every tenant sends from one fixed TideGrid address. A tenant's brand chooses the name a guest sees, so without a guard a brand could make an email look as if TideGrid staff, another operator, or a system mailbox sent it. The guard below closes that, as the coordinator default D1 (2026-11-08, pending owner confirmation): the display name reads "Brand Name via TideGrid", with the fixed TideGrid address. The two alternatives, a reserved-name refusal alone or a verified reply-to table, stay proposed and not built. No migration.

- **The sender name rule.** `senderNameProblem` in `@tidegrid/contracts` (`packages/contracts/src/brand.ts`) decides whether a name may lead a sender display name. It refuses:
  - any character but Latin letters, ASCII digits, single spaces, and `& ' ’ . , ! ( ) / + # -`. That refuses CR, LF and every other control (no header injection), every Cf format character (zero-width characters, bidi overrides, the byte order mark, the soft hyphen), quotes, `@`, `:`, `;`, angle brackets and backslashes (no address lookalike), Cyrillic or Greek letters (no cross-script confusable), and the Latin Roman numerals that NFKC leaves alone, U+2180 to U+2182 and U+2185 to U+2188 (recheck fix, 2026-11-08). A name must be in composed, compatibility-folded form, so fullwidth letters and decomposed accents are refused too;
  - a Latin letter that does not fold to a to z, such as "ɨ", "ɖ", "ǀ", "ɛ", or a small capital outside the table, and a number that does not fold to a letter or an ASCII digit. Every letter therefore counts in the skeleton below; none is silently dropped (review fix, 2026-11-08);
  - a name whose skeleton contains TideGrid's under some reading of its digits and "!" marks. `senderSkeleton` folds compatibility forms, drops accents, lowercases, folds a table of Latin, Cyrillic and Greek lookalikes and of digits and symbols read as letters, reads `l` as `i`, `rn` as `m`, `vv` as `w`, and `cl` as `d`, and keeps a to z. "T1de Gr!d", "TideGricl", "Tídé Gríd", and Latin small capitals all read as `tidegrid`. Since the second pull request review (fix G2), each digit or "!" may also read as nothing, as it does when it stays a digit or separates, so "Tide!Grid", "T!de!Gr!d", and "Tide1Grid" are refused too. A linear scan over the characters decides it, and a test checks it against every reading of generated names;
  - a name made only of staff, mailbox, department, and filler words, such as "Support", "Billing Team", "No-Reply", "Do Not Reply", "Billing Dept", "Help Center", or "The Security Team". Digit-only words and words of one letter are ignored, so "Support Team 2" and "Security Team 1" are refused too. "Harbor Support" passes: it names its operator;
  - "via" after the first word ("Harbor via Stripe" would name a second relay), also when spelled with lookalikes or split by separators. A longer word that only contains it, such as "Trivia", "Avian", or "Viaduct", passes. A domain-like word ("paypal.com") is refused too.
- **Digits and "!" are read every way (pull request review fix, 2026-11-08).** Earlier rounds checked a fixed set of word splits, and each round found a narrower bypass, because no split read a "!" and a digit with different meanings together ("B!lling1", "Harbor v!a1 Stripe"). The rule now classifies each character. A Latin letter reads as its folded letters. A space, or punctuation that folds to no letter, is a hard separator. A digit, or "!" (it folds to "i"), is ambiguous: it may read as its letter, stay a digit, or separate words. A name is refused if some reading of it fires either check, or if it has too many such characters:
  - staff words: some reading splits the name into words that are all staff, mailbox, department, or filler words or ignorable (digits, one letter), with at least one staff word. A word break over the characters decides this in polynomial time without listing readings. "Support!", "No!Reply", "Support1", "B!lling Team", "B!lling1", and "B!lling!Team" are refused;
  - a second relay: after word content, some run of characters that starts right after a separator, ends at the end or right before one, and reads exactly "via" once the separators inside it are dropped. "Harbor v!a Stripe", "Harbor v.i.a Stripe", "Harbor V I A Stripe", "Harbor Vi A Stripe", "Harbor via1 Stripe", "Harbor v!a1 Stripe", and "Harbor V!A!Stripe" are refused. "V!a Ferrata Tours" and "V.I.A. Harbor Tours" pass: "via" leads them;
  - the bound: a name may carry at most 12 digits and "!" marks (`maxSenderAmbiguousCharacters`). The checks do not need the bound for speed. It keeps every name's readings, at most 3^12, small enough to enumerate as a cross-check, and a founding year with a seven-digit phone number still fits. A brute-force check of every reading agreed with the rule on about 200,000 generated names during the fix.
- **Brand validation.** `BrandConfig` applies the rule to `name`, and refuses a `contact.email` whose domain or local part reads as TideGrid (`contactEmailProblem`), so "support@tidegrid.us" and "tidegrid.support@demo-harbor.test" are both refused. Digits in an address are read as for a name, so "tide1grid@demo-harbor.test" is refused (fix G2). A contact domain with an IDNA label (`xn--`) is refused outright (fix G3): "support@xn--tdegrd-pvfe.test" is ASCII, but a mail client shows it as a Cyrillic TideGrid lookalike. Decoding and folding it would need a confusable table for every script, and the address rule already admits only ASCII, so refusing the ASCII form of a Unicode domain is the narrower safe choice. The reply-to is still not verified (see the residuals). The published OpenAPI pattern is unchanged; only the field's description says so. Every boundary that reads a brand already parses it with `BrandConfig`, so a stored brand that fails is withheld from the guest site and treated as no brand in email.
- **Binding to the provisioned name.** `loadEmailBrand` uses a brand's name only when it reads as the tenant's provisioned display name (`sameSenderName`: both names pass the rule, and the folded letters and digits match, ignoring spaces, case, accents, and punctuation that reads as no letter). Since the pull request review fix, a brand never binds to a provisioned name the rule refuses, so "B!lling1" cannot bind to "Billing1". Text cannot be appended to a provisioned name: "Demo Harbor Charters 2" does not bind to "Demo Harbor Charters". TideGrid sets `tenants.display_name` when it creates a tenant, and the runtime role cannot insert or update it. A brand that names another operator therefore sends, and renders, under its own provisioned name. A provisioned name that fails the rule becomes "Your trip operator".
- **Rendering.** `renderEmail` applies the rule again to the brand it is given (`emailOperatorName`): a failing name renders and sends as "Your trip operator". It returns `fromName`, the operator's name and " via TideGrid" (`emailSenderName`). For the two synthetic brands the subject and both bodies are byte for byte what they were before the guard (a hash test in `src/render.test.ts` pins the baseline output).
- **At delivery (fix G1).** The stored sender is never trusted as written. When delivery claims a message it loads the tenant's current email brand (`loadEmailBrand`) and checks the stored `from_name` and `reply_to` against it (`deliverySender` in `src/brand.ts`). A stored name is kept only when it reads as the bound brand name (`sameSenderName`); otherwise the bound name replaces it: the provisioned name, or "Your trip operator". A stored reply-to that `contactEmailProblem` refuses is dropped. So a message queued before the guard, or written by any path other than `enqueueMessage`, cannot send as another operator or with a TideGrid-looking reply-to, through any provider. `deliverTenantMessages` and the sweep both claim through this one path, and it is the only code that calls a provider with a stored message.
- **At the wire.** The Cloudflare adapter builds the display name with `senderDisplayName`: the name it is given, without a trailing " via TideGrid" if present, then the suffix once. A name that fails the rule is refused as `invalid_message` with no provider call. Messages enqueued before the guard, which store the bare brand name, gain the suffix here.
- **Tests.** `packages/contracts/src/brand-sender.test.ts` (the rule and brand validation: lookalike names, Unicode confusables, Cf characters, CR and LF, reserved names, addresses and domains), `src/render.test.ts`, `src/cloudflare.test.ts`, `src/brand.test.ts` (`deliverySender`), and `src/sender-guard.integration.test.ts` (stored brands and provisioned names against PostgreSQL 17, the Cloudflare fixture's builder, and pending messages stored with another operator's name and a TideGrid-looking reply-to, delivered through the Cloudflare fixture and the fake provider).

### Residuals

- **The stored `from_name` has no suffix.** `enqueueMessage` stores the bound operator name, not `RenderedEmail.fromName`, since `src/enqueue.ts` was outside this goal. The Cloudflare adapter adds the suffix; the fake provider and its local mailbox show the bare name. Proposed: store `fromName` in a later messaging goal.
- **A legacy message's bodies keep their stored name.** Delivery replaces a stored sender name that does not bind (fix G1), but the bodies were rendered at enqueue and are not rendered again, so a message queued before the guard can still name another operator in its header row and footer. Only messages queued before the guard, or written outside `enqueueMessage`, are affected. Proposed: fail such a message at delivery instead of sending it, if the owner prefers no send to a corrected header.
- **Two tenants could be provisioned with confusable names.** Nothing in the database makes `tenants.display_name` unique by skeleton; the binding relies on TideGrid not provisioning two operators under one name. Proposed: a uniqueness check by skeleton at provisioning.
- **The reply-to is not verified.** A brand's contact email becomes the reply-to without proof that the operator owns it. A verified reply-to table stays proposed (D1's third option).
- **Latin script only.** The rule refuses non-Latin letters, which fits the en-US-only brand locale. A localized brand would need a script-aware confusable check.
- **Not every lookalike.** The skeleton table is hand-written, not the full Unicode confusables data. A Latin letter outside the table that does not decompose to a to z is refused, not dropped, so the table limits which names are accepted, not what the checks see. A lookalike that folds to a different ASCII letter than the one it imitates could still pass, though it would carry the " via TideGrid" suffix and the fixed TideGrid address.
- **Words joined with no separator.** A relay or staff words joined to other letters with no separator still pass: "Harbor ViaStripe", "SupportTeam", "BillingDept". Splitting at a case change would also refuse names such as "Viaduct Tours". In email the binding to the provisioned name still applies.
- **Staff words are a list.** The staff, department, and filler list is hand-written. A staff-sounding name built from a word outside it can pass brand validation. In email the binding to the provisioned name still applies, so such a name sends only if TideGrid provisions it.
- **The tightened rule also gates the guest site.** `BrandConfig` now refuses names that passed before, such as "Harbor: Charters" or "Riptide Gridiron Tours" (its letters contain TideGrid's). A stored brand like that is withheld from the whole guest site, not just from email. The two synthetic brands pass. No check runs the rule over stored `brand_config_versions` rows; proposed: run every active brand through `BrandConfig` before any non-synthetic brand is stored.

## Staff resend claims (W1-RESEND-CLAIM)

The delivery job's claim meets the staff resend limits again, at the moment it claims (migration `0017`; see the [database README](../database/README.md#staff-resend-claims-0017)). `claimOne` takes the tenant's resend lock (`RESEND_LOCK_PREFIX`, the key the booking module's `resendBookingEmail` takes first) before it locks any message, without waiting: while a resend or another claim holds it, the run claims nothing for that tenant, and a later run does. Its pick skips a `booking.resend:` message (`RESEND_KEY_PREFIX`) whose claim must wait (`RESEND_WAIT_CODES`: `resend_interval`, `resend_rate`), and claims the next due message instead; the resend is claimed at a later run once its wait lifts. A resend whose claim can never go ahead (`resend_limit`, `resend_unrecorded`) is canceled with that code, its links revoked as `withdrawn`, and reported as `canceled`. The claim guard in the database decides again for every writer; the job reads the same rules under the same lock first, so it does not meet the guard's error. Every other message is claimed exactly as before, after the same lock.

## Booking email keys (W1-0014-RESIDUALS)

Since migration `0019` (see the [database README](../database/README.md#staff-resend-residuals-0019)), a `booking_confirmation` or `booking_canceled` message enqueues only with its booking's id and that booking's own key: `booking.confirmation:<booking>`, `booking.canceled:<booking>`, or a staff resend's `booking.resend:<booking>:<n>`. ## Email events (W1-EMAIL-EVENTS)

Bounces and spam complaints the provider reports after it accepted a message now reach staff: the booking's Email card shows "Bounced" or "Marked as spam" in place of "Sent", with what to do. Built and tested locally only. The owner pulled the goal forward on 2026-11-08; the choices below are coordinator defaults, pending owner confirmation ([decision register](../../docs/v2/06-decision-register.md)). Migrations: [0021 and 0022](../database/README.md#email-events-0021-and-0022).

```ts
parseCloudflareEmailEvent(body: unknown): { kind: "parsed"; event } | { kind: "invalid"; reason }
emailEventsConfig(accountId?, sendingDomain?): { accountId; sendingDomain } | null
ingestEmailEvent(db, config, body): Promise<{ outcome; reason?; eventType?; tenantId?; messageId? }>
// outcome: applied | recorded | duplicate | unmatched | ignored | refused_account | refused_domain | invalid
```

- **Delivery is a queue, not a webhook (D2).** Cloudflare publishes Email Sending events only to a Cloudflare queue through an event subscription, and signs nothing ([event subscriptions](https://developers.cloudflare.com/email-service/reference/event-subscriptions/), read 2026-11-08). The goal's recommended signed webhook route does not exist on Cloudflare's side, so the API Worker gets a queue consumer instead (`apps/api-worker/src/email-events.ts`, the `queue` handler in `src/index.ts`), with no route, no body cap entry, and no binding in the repository. The queue's trust comes from the platform: only the account's own subscriptions and producers can publish to it. That is the only authentication. The account and domain checks below are claims in the event's body, so no other Worker may hold a producer binding to this queue, and API tokens with Queues write stay few (security review, medium, recorded).
- **Whose events (refused, never recorded, retried).** The event's `metadata.accountId` must equal `EMAIL_EVENTS_ACCOUNT_ID` (a secret, never in the repository), and its `source.domain` must equal the domain of `EMAIL_FROM_ADDRESS`, exactly: a parent or another subdomain is refused. A refused event is retried, not acknowledged, so a wrong setting sends real events to the queue's dead-letter queue instead of dropping them; give the queue a retry limit and a dead-letter queue when it is created. Only schema version 1 is read; any other is refused as invalid and logged. So is a time before 2020 or after 2099, and the adapter's own stand-in id (`cf_no_id.<message>`), which Cloudflare never sends and anyone could guess.
- **Which events.** `bounced` and `complained` are kept, when final (`payload.terminal` is not false). `delivered`, `deferred`, `failed` and `rejected` are acknowledged and dropped: a deferral is not an outcome, and a suppressed recipient is refused by `send()` itself while "Drop suppressed recipients" is off, as the runbook sets it. Whether `failed` or `rejected` can ever follow an accepted send is unproven until A9; if one can, it should become a report too (independent review, recorded).
- **The join (D1).** `payload.messageId` goes through `normalizeCloudflareMessageId`, the rule the adapter applied when it stored the id at send, then `app.resolve_email_message`. Exact match after that rule is the coordinator default. The live comparison of the id `send()` returns with an event's `payload.messageId` (O-P7 A9: brackets, domain, form) has not run, so the join form is unproven against the real service. If they differ, the fix is in the normalization, before the join.
- **Once.** The first bounce or complaint for a message is applied; a later one is kept, not applied; the same event id again changes nothing. An id that joins no sent message is recorded once, joined to nothing. A race between two events for one message applies exactly one.
- **Retries.** Each queue message stands alone. A database error, a refused account or domain, or an event in a shape this code does not know (another schema version, type, or source) retries that message, after 30 seconds doubling per attempt up to an hour; every other outcome is final and acknowledged. Without a valid account id or a database the whole batch is retried after ten minutes. The queue's retry limit and dead-letter queue then decide what happens to events the consumer keeps refusing.
- **Nothing personal.** No recipient, sender, subject, or SMTP text is stored or logged. Logs carry the outcome, the event type, and the tenant and message ids.
- **Staff read.** `MessageStatus.deliveryReport` is `{ kind, bounceType, detailCode, reportedAt }` or null; the state stays `sent`. The console reads a missing field as null, so an older API still renders.
- **Late joins.** An event that arrives before its message is recorded as sent (the provider id is stored after `send()` returns) is recorded as unmatched and never joined later; staff keep seeing "Sent" (recorded).
- **Not built.** The live event subscription, the queue, its consumer binding, and the account id secret: owner steps. Suppression changes, per-operator sending domains, and the exceptions list (W1-EMAIL-EXC still lists failed email only). The unmatched table has no reader.
- **Tests.** `src/events.test.ts` (parsing), `src/events.integration.test.ts` (E1 to E10 on PostgreSQL), `apps/api-worker/test/email-events.test.ts` (the queue handling), and the console's Email card tests. The event shapes are recorded from the documentation in `src/cloudflare-events-fixture.ts`, with synthetic values; no live event has been seen.

## Sender domains and suppression (W3-G2.16-rest)

Pulled forward as code only on 2026-11-08 ([decision register](../../docs/v2/06-decision-register.md)); coordinator defaults D1 to D6, pending owner confirmation. Tables are in migration `0027` ([database README](../database/README.md#sender-domains-and-suppression-0027)); the code is `src/sender.ts`, the claim in `src/delivery.ts`, and the consumer in `src/events.ts`. Nothing here onboards a domain with the provider or changes DNS.

- **Who sends.** Delivery decides the sender when it claims a message, in the claim's transaction. An operator with a verified sending domain sends from `<mailbox>@<domain>`; the display name is unchanged ("Operator Name via TideGrid", [sender identity](#sender-identity-w1-sender-guard)). Otherwise `DeliveryOptions.senderPolicy` decides: `shared` (the default) uses `fromAddress`; `operator_only` claims nothing for that operator, its mail stays queued, and the run reports `held: "sender_unverified"` (the sweep counts `heldTenants`, gives that operator no second turn, and goes on to the next). A held operator's lapsed attempt still ends as `outcome_unknown` on a provider that does not deduplicate, so nothing sits in `sending` while it is held. The after-commit log line carries `tidegrid.email.held`. The API passes `EMAIL_SENDER_POLICY`: unset, `operator_only` in production and `shared` elsewhere; any other value refuses email.
- **Only a verified domain.** The runtime can read `tenant_sender_domains` and nothing more. Only the admin connection adds, verifies, and retires a domain, through the [email CLI](../../tools/email/README.md), so mail never goes out from a domain nobody checked. Retiring a domain sends the operator's mail back to the shared sender, or holds it under `operator_only`.
- **A refused operator sender.** An account-level fault met on an operator's own address holds that operator's run only, with the attempt given back as for any account-level fault: `sender_not_verified` (the binding does not allow the address yet, or Cloudflare has not verified the domain) as `held: "sender_unverified"`, and any other, such as a daily limit Cloudflare may count per domain, as `held: "sender_fault"`. A suspended account (`provider_account_suspended`) still stops the sweep, and from the shared sender every account-level fault does, as before (security review M2).
- **Suppression.** A complaint, or a terminal hard bounce, newly recorded by the events consumer suppresses the message's address for its operator, in the same transaction (`IngestResult.suppressed`). A soft bounce suppresses nothing. At the claim, a message to an address its operator suppressed fails as `address_suppressed` with no provider call and no link issued; another operator's mail to the same address is unaffected. Only the admin lifts a suppression (`email suppression-lift`), with a reason; the audit row names the suppression's id, never the address. Staff lifting from the console is a proposed follow-up.
- **Events from operator domains.** The consumer accepts the shared domain at once. A dropped type (delivered, deferred, failed, rejected, or a bounce that is not final) from another domain is acknowledged only if some operator has that domain verified now, so a wrong sending domain setting still sends events to the dead-letter queue. Another well-formed domain is checked in the database: for an event that joins a message, a domain that message's operator verified (now or before, so a retired domain's late events still land); for one that joins nothing, a domain some operator has verified now (`app.email_sender_domain_known`, which says nothing about retired domains or which operator). Anything else is `refused_domain` and retried, as before.
- **Residuals.** The message does not record which address sent it, so an event from any domain its operator ever verified is accepted for any of its messages (proposed: store the sending domain on the message at its claim). Cloudflare documents its suppression as per account or per sending domain, without saying which applies when: if it is per account, one operator's complaint still makes Cloudflare refuse another operator's mail to that guest (`recipient_suppressed`) even from its own domain, so TideGrid's per-operator suppression holds only for TideGrid's own list until Cloudflare confirms the scope (security review M1, an owner question). The runtime is still trusted to record what the queue gave it (0021): a writer holding its credentials can record a made-up complaint for its own tenant's sent message, and so suppress that address within its own tenant. Evidence and reasons given to the CLI are audited, so the CLI refuses text with an address in it; `suppression-lift` takes the guest's address on the command line, so it is in the shell's history.
- **Tests.** `src/sender.integration.test.ts` (S1 to S11, with S2b and S4b: the sender before and after verification and retirement, `operator_only` holds, the sweep holds one operator and serves another, a refused operator sender, runtime privileges, the database rules, suppression for one operator only, soft bounces, lifting, forged suppressions, and the consumer's domain check), `apps/api-worker/test/email.test.ts` (the policy setting), and `tools/email` (the CLI).

## Trip reminders (W3-G2.16-rest)

A guest gets one reminder a day before the trip leaves, with a fresh management link. Code only, no migration: it rides on the queue's `notBefore`. The booking module writes it (`enqueueReminderEmail` in [domain-booking](../domain-booking/README.md#guest-self-service-lane-1-g211c)); this module owns the rule that keeps it from arriving too late (`src/reminders.ts`).

- **Written with the booking.** The confirming transaction writes the reminder beside the confirmation, under its own savepoint, keyed `booking.reminder:<bookingId>` (once per booking), template `booking_reminder`, due `TRIP_REMINDER_LEAD_HOURS` (24) before departure. A booking made within two days of departure (`TRIP_REMINDER_MIN_NOTICE_HOURS`, 24 hours before the reminder's due time) gets none: its confirmation is recent enough to be the reminder. A failure to write it never undoes the booking; it records `booking.reminder_email_failed` (audit and outbox, an ops alert topic) and leaves the confirmation queued.
- **Nothing else schedules it.** The delivery sweep claims only due messages, so the reminder waits in `queued` until its day. The console labels a queued message that is not due yet "Scheduled", and the booking's message list puts the reminder after the confirmation written with it.
- **Never too late.** A retry can wait for hours, so the claim checks again: a `booking_reminder` whose booking was canceled or is gone, whose trip was canceled, or whose trip leaves within `TRIP_REMINDER_CUTOFF_HOURS` (2, as for waiver reminders) is canceled as `reminder_too_late`, with no provider call and no link issued. The claim reads the booking `FOR SHARE SKIP LOCKED`: while a cancellation holds it, this run passes the reminder over, without counting it against the run's limit, and goes on to the operator's other mail (a sweep remembers what it passed over across a tenant's turns, and a run passes over at most 50 before it ends), and a later run picks it up, so it never goes out as the cancellation commits. The check comes after the lapsed-lease rule, so an attempt that may already have reached the guest ends as `outcome_unknown` on a provider that does not deduplicate, and no link is revoked on this path. Canceling the booking also cancels the waiting reminder at once (`booking_canceled`).
- **The link.** Sending it issues a management link. The reminder is written with the confirmation, so which of the two counts as newer for superseding is not fixed; the email does not claim earlier links stopped working, and a superseded link still renews.
- **Residuals.** The words are rendered when the booking is made, as every message's are, so a later change to the meeting point or the operator's brand is not in it. Nothing in the app moves a trip's departure today; if that is built, the move must re-time or cancel the booking's reminder (a trip moved earlier keeps the old due time, and the claim's cutoff check is then the only guard).
- **Tests.** `packages/domain-booking/src/adversarial/trip-reminder.integration.test.ts` (written and due a day ahead, sent with a working link, written at 49 hours out and not at 47, canceled with the booking, canceled at claim within two hours of departure and for an already canceled booking, a lapsed attempt near departure ending as `outcome_unknown` or canceled by provider with its issued link still live, a reminder whose booking is locked passed over while other mail goes out, and a reminder that cannot be written leaving the booking and its confirmation in place), and the console's model tests.

## Balance reminders (W3-G2.8)

Two templates for private-charter balances: `booking_balance_reminder`, due 7 days and 1 day before the balance's due date, and `booking_balance_link`, which staff send on request. When one is claimed, `balanceEmailTiming` checks the booking again: nothing owed any more (paid, canceled, or the trip left) cancels it unsent with `balance_settled`, and a booking held by another change is left for a later run. Neither states the amount, which may change after it is written; the link shows it.
