# @tidegrid/database

PostgreSQL access for the TideGrid demo build: Kysely over postgres.js, reviewed SQL migrations, and the tenancy primitives every domain module uses. This file is the working contract for tenant isolation. The design authority is the [target architecture](../../docs/v2/04-architecture.md) and the retained V1 decisions on [tenancy](../../docs/v1/adr/0003-postgresql-tenancy.md), [row-level security](../../docs/v1/adr/0004-row-level-security.md), [outbox](../../docs/v1/adr/0008-transactional-outbox.md), and [audit](../../docs/v1/adr/0018-audit-log.md).

## Roles

- **Admin (the database owner; on Neon, the owner role).** Runs migrations and seeds. Bypasses row-level security. Never used by a Worker.
- **`tidegrid_app`.** The only role a Worker uses. Created in SQL by migration 0001 with no elevated attributes; never create it through the Neon console or API, because those roles join `neon_superuser` and bypass row-level security. It gets privileges only from migrations. The migration runner, before and after every run, and the password command (`pnpm --filter @tidegrid/database app-role:password`) refuse a `tidegrid_app` that is more than that plain role: any elevated attribute including REPLICATION, membership in any role (SET ROLE through a chain can reach one that bypasses row-level security), or ownership of any object. Neon accepts only plaintext passwords over its control plane, so the password is sent once over TLS.

## Tenant isolation rules

1. Every tenant-owned table has a `tenant_id` column, row-level security enabled and forced, and a `tenant_isolation` policy on `app.current_tenant_id()` for both reads and writes.
2. Every read or write of a tenant-owned table runs inside `inTenantTransaction`, which sets `app.tenant_id`, the actor, the request id, and the source address with `set_config(..., true)`. The settings are transaction-local, so a pooled connection never carries one request's tenant into the next.
3. Queries also filter by tenant explicitly. Row-level security is the backstop, not the mechanism.
4. Without context the runtime sees no tenant rows and can write none. A malformed tenant id raises instead of matching.
5. The runtime holds SELECT and INSERT by default. UPDATE is granted column by column in the migration that needs it. DELETE and TRUNCATE are never granted; state changes are appends or status updates.
6. Platform credential tables (`staff_login_tokens`, `staff_sessions`, `security_events`) grant the runtime nothing. It reaches them only through the SECURITY DEFINER functions in schema `app`.
7. Every function in schema `app` has EXECUTE revoked from PUBLIC. Every SECURITY DEFINER function pins `search_path = pg_catalog, pg_temp`, qualifies every relation, and filters explicitly because its owner bypasses row-level security.
8. The runtime cannot create objects anywhere: no CREATE on any schema and no TEMPORARY on the database.
9. Staff identities are global and their addresses are ASCII, so case folding cannot turn a lookalike character into someone else's address. A tenant reads an identity's id, email, status, and creation time only; the name a tenant shows lives on its own membership row, so no tenant can read or set what another tenant sees.
10. A reference from one tenant row to another includes `tenant_id` in a composite foreign key, as the catalog tables in 0003 do, so a row cannot point at another tenant's row even when application code passes the wrong id.

The integration suite enforces rules 1, 5, 6, 7, 8, and the column limits in rule 9 from the catalog, so a later migration that forgets them fails CI. The catalog suite checks rule 10 by trying cross-tenant references.

## Behavior by design, and known gaps

- `app.auth_list_memberships` returns the memberships of whatever user id it is given. The API passes only the authenticated principal's own id.
- A session-level `set_config(..., false)` would survive on a pooled connection. Nothing in the codebase does that, and `setTenantContext` refuses a connection that already carries a tenant.
- Disabling an identity revokes its sessions (W3-G2.2b), so re-enabling revives none. Disabling a membership revokes the person's sessions only when it was their last active one; until then the per-request membership check ends that tenant's access.
- Replayed idempotent responses are equal field for field, not byte for byte, because `jsonb` reorders keys. Completed keys are kept for seven days past `expires_at`, then removed by `app.delivery_cleanup` (0023). A client that retries with the same key after that runs the command again.
- Audit and outbox ids come from one sequence per table, so a tenant can infer overall platform volume from gaps. Acceptable for the demo; revisit before the pilot.
- A person added to a tenant is invited and gets no access until they accept (W3-G2.2b). No invitation email is sent yet: the person signs in and finds the invitation in the console.

## Commands, audit, idempotency, and outbox

A state-changing command follows one shape, all inside one tenant transaction:

1. Authorize (the API checks membership and permission first).
2. `claimIdempotencyKey` before any domain write. A concurrent duplicate blocks on the key until the first commits, then replays its stored response. A failed command rolls back its claim. The request hash covers the method, route template, every path id, and the body, so the same key sent for another resource is refused, never replayed.
3. Write domain state.
4. `recordAudit` with the action, subject, reason, and before and after values. Audit rows are append-only for every role, including the owner.
5. `enqueueOutbox` for any event other modules or providers need. The row exists only if the command commits.
6. `completeIdempotencyKey` with the successful response.

Keys are scoped by tenant, operation, and principal. Only successful responses are stored.

A read whose statements must agree with each other, such as a page and the counts beside it, passes `snapshotRead` as `inTenantTransaction`'s last argument (G2.12b): the transaction runs REPEATABLE READ and READ ONLY, so every statement sees the moment of the first and nothing can be written. The level is set before the tenant context, because PostgreSQL fixes it at the first statement. Commands keep the default READ COMMITTED, which their locking needs. `src/snapshot.integration.test.ts` holds this.

## Brand configuration

Migration 0004 adds two tenant-owned, append-only tables under rules 1 to 8:

- `brand_config_versions`: one row per published brand, keyed by tenant and a per-tenant version number, holding the brand contract's `BrandConfig` (`packages/contracts/src/brand.ts`) as bounded JSON with its schema version. Writers validate the config against the contract before insert.
- `brand_activations`: who made which version live, when, and why. Its foreign key includes `tenant_id`, so an activation can only name its own tenant's version. The tenant's latest activation (highest id) is its active brand.

The runtime holds SELECT and INSERT on both. UPDATE, DELETE, and TRUNCATE raise for every role, the owner included, so an old version never changes; returning to an earlier brand is a new activation. Publishing is one tenant transaction: insert the next version, insert its activation with a reason, and record an audit event.

The active brand is simply the highest activation id, and nothing in the schema serializes two publishes for the same tenant. Any publish command, today's seed or a future staff command, must therefore first take the per-tenant transaction lock the seed takes, `pg_advisory_xact_lock(hashtextextended('tidegrid.brand:' || tenant_id, 0))`, before reading the current version. Without it, two concurrent publishes can compute the same next version number (one fails on the unique key) or activate in the opposite order from the one their callers saw.

`app.resolve_public_brand(hostname)` is the public bootstrap. It resolves the hostname through `app.resolve_hostname`, so only active, verified hostnames of active tenants return a row, and joins that tenant's active brand, filtering by the resolved tenant explicitly. The brand columns are NULL until the tenant publishes one. The API validates the stored config against the contract again before serving it, and fails closed if it does not validate.

## Pricing, policies, and quotes

Migration 0005 adds ten tenant-owned tables under rules 1 to 10, described in the [pricing contract](../domain-pricing/README.md): `price_list_versions` and `price_list_items`, `policy_versions`, `tax_rate_versions`, `promotions`, `promotion_versions` and `promotion_version_products`, and `quotes`, `quote_lines`, and `quote_line_taxes`.

- **Append-only for every role.** The runtime holds SELECT and INSERT. UPDATE, DELETE, and TRUNCATE raise for everyone, the owner included. A change is a new version; the highest version is current.
- **Sealed children.** A price list version, promotion version, or quote records the transaction that created it (`created_txid`) and the database time it was written (`created_at`). A trigger stamps both, so no writer can choose them. Its items, products, lines, or line taxes can be written only by that transaction, savepoints included, so nothing grows after commit.
- **Checked when written and at commit.** When a quote is written, its trip snapshot must equal the trip it names, its party must be within the product's limits and the trip's seats, and it must be dated before the trip departs. Deferred constraint triggers, owner-run with explicit tenant filters, refuse at commit a shared-seat price list with no ticket type, a charter price list without its price, a quote whose header totals differ from its lines, and a quote its named versions do not produce: lines not copied from the price list version, missing fees, a promotion outside its window or rule or without its label, a discount split other than by the largest remainder, or taxes that do not follow their rates. `app.discount_label` gives the label the check expects; like every function in schema `app`, the runtime cannot call it.
- **Quote validity.** `quoted_at` and `expires_at` come from the writer, so they bound an honest quote only. Checkout must accept a quote only while `now() < least(expires_at, created_at + interval '30 minutes')` on the database clock, as the [pricing contract](../domain-pricing/README.md#quotes) says.
- **Kinds in keys.** `products` gains `UNIQUE (tenant_id, id, kind)` and `scheduled_trips` gains `UNIQUE (tenant_id, id, product_id)`, so a price list cannot carry the wrong product kind and a quote cannot pair a trip with another product.
- **Publishing.** A trigger on `products` refuses publishing a product without a price list and a policy, for every writer.
- **Actors.** A trigger stamps `actor_type`, `actor_id`, and `request_id` from the transaction's context on every version, promotion, and quote row, so no writer can name another actor. Version and promotion rows refuse the guest actor type through their `actor_type` check, so a guest may create quotes only.
- **Numbering.** Commands that append a version take a per-aggregate transaction lock, such as `tidegrid.price_list:<tenant>:<product>`, before reading the current version, as brand publishing does.

## Capacity holds

The capacity and holds migration adds `capacity_holds` under rules 1 to 10. The contract, the concurrency design, and the clock decision are in the [inventory README](../domain-inventory/README.md); what matters for tenancy:

- The runtime keeps the default SELECT and INSERT and may UPDATE `state` only. A trigger sets the kind, the seats taken, and every timestamp but the expiry instant, which can only move earlier. It enforces the one-way states and the capacity rule for every role, and refuses DELETE and TRUNCATE for every role, the owner included. A second trigger, on `scheduled_trips`, keeps a trip's capacity and product from changing under its holds.
- The trigger runs as the caller. It reads the trip under the caller's row-level security and filters by the hold's tenant, so a hold can never name another tenant's trip; the composite foreign key backs that up.
- `app.trip_capacity_usage(tenant, trip)` is an invoker function. Row-level security applies inside it, and it filters by tenant explicitly.

`app.capacity_hold_sweep_tenants(limit)` lets the cron sweep find the tenants with holds past their expiry instant. It was the first of the runtime's cross-tenant sweep reads, beside sign-in and hostname resolution; `app.checkout_sweep_tenants` (0007), `app.email_delivery_tenants` (0009), and `app.hostname_sweep_tenants` (0011) follow the same argument:

- It returns tenant ids and nothing else: no hold, trip, owner, or count. An id grants nothing. Every read and write that follows runs in `inTenantTransaction` under forced row-level security, and tenant ids already appear in staff URLs.
- What it reveals is that some tenant has at least one stale hold. That is a weaker activity signal than the shared audit and outbox id sequences already give (see the known gaps above).
- It is read-only and STABLE, a SECURITY DEFINER function with `search_path` pinned, every relation qualified, explicit predicates, and at most 1,000 rows. EXECUTE is granted to `tidegrid_app` only.
- The alternatives are worse. A row-level-security bypass for the cron's connection would expose every tenant's rows to one session. A tenant list in configuration drifts from the database and would silently skip new tenants. One definer function that expired holds across tenants would write audit and outbox rows outside any tenant's transaction.
- **Order.** Since 0013 each orders by its sweep's stamps (see [Sweep turns](#sweep-turns-0013)).

## Checkout, payments, and bookings

The checkout migration (0007) adds twelve tenant-owned tables under rules 1 to 10, described in the [checkout contract](../domain-booking/README.md) and the [payments contract](../domain-payments/README.md): `checkout_sessions`, `orders` and `order_lines`, `payments`, `payment_refunds`, `provider_events` (the inbox), `bookings`, `finalization_exceptions`, `payment_accounts`, and the fake provider's `fake_provider_payments`, `fake_provider_events`, and `fake_provider_refunds`.

- **Privileges.** The runtime keeps the default SELECT and INSERT, except on `payment_accounts`, which it may only read: onboarding (the seed) writes where money goes, never a request. UPDATE is granted only on the columns that carry a transition: `checkout_sessions.state`, `orders.status`, `payments` (`state`, `provider_payment_id`, and the two evidence columns), `payment_refunds` (`state`, `provider_refund_id`, `failure_code`), and `provider_events` (`processing_state`, `outcome`). Triggers stamp every time from the database clock.
- **No deletes.** DELETE and TRUNCATE raise on every table here for every role, the owner included. Order lines, bookings, exceptions, and the fake provider's tables refuse UPDATE too.
- **States and evidence for every role.** Triggers run as the writer, under its row-level security, and filter by tenant explicitly. They enforce the one-way states and the chain of custody: a checkout confirms only with a booking, a booking needs a succeeded payment and a confirmed hold, an order is paid only with a booking, and a payment succeeds only with a verified inbox event for its provider id, account, amount, and currency. The owner role cannot skip a link either.
- **Sealed and self-checking orders.** Order lines can be written only in their order's transaction, and a deferred check refuses at commit an order that does not equal its quote, line for line and tax rate for tax rate.
- **Composite keys.** Every reference carries `tenant_id`, including the inbox's reference to the connected account, so an event can be recorded only in the tenant that owns the account it names.
- **Trips with bookings.** A trigger on `scheduled_trips` refuses canceling a trip that has confirmed holds, under READ COMMITTED only, until cancellation with remedies exists.
- **Holds behind checkouts.** Two triggers on `capacity_holds` keep holds and checkouts in step: a hold that backs a confirmed booking cannot be released while the booking stands, and, at commit, a checkout's hold is confirmed only with its booking and is not released while its checkout is open.
- **Booked or refunded, never both.** Inserting a booking or a refund locks the payment's row and refuses the one when the other exists.

Two more cross-tenant reads join `app.resolve_hostname` and `app.capacity_hold_sweep_tenants`. Both are read-only, STABLE, SECURITY DEFINER with `search_path` pinned, every relation qualified, and EXECUTE granted to `tidegrid_app` only:

- `app.resolve_payment_account(provider, account_ref)` returns the tenant id and the account's status for a connected account. A provider callback names an account, not a tenant, and the webhook must record the event inside the owning tenant's transaction. It runs only after the provider's signature verifies, an id grants nothing, and everything that follows runs under row-level security. It returns accounts whatever their status, because money that moved must be recorded.
- `app.checkout_sweep_tenants(limit, grace_seconds)` returns, at most 1,000, the tenant ids with an open checkout past its instant, or a refund requested or an inbox event received at least the grace period ago (0 to 3,600 seconds) and never settled or processed. It reveals that some tenant has such work, a weaker signal than the shared id sequences already give, and the sweep then works inside each tenant's own transaction, for the reasons the hold sweep's argument gives.

## Booking notes

The console completion migration (G2.12c, numbered 0008 on its branch) adds one tenant-owned table, `booking_notes`, under rules 1 to 10. The commands are in the [checkout contract](../domain-booking/README.md#console-completion-g212c).

- **Append-only for every role.** The runtime keeps the default SELECT and INSERT and receives nothing more. UPDATE, DELETE, and TRUNCATE raise for every role, the owner included (`app.reject_mutation`).
- **The author is the transaction's.** A trigger (`app.stamp_booking_note`, an invoker function with `search_path` pinned and no EXECUTE for anyone) sets the author from `app.actor_id`, and the request id and the time from the transaction, whatever the insert names. It refuses a note unless the actor is staff with a UUID id (SQLSTATE 42501, `booking_notes_staff_author`), so a guest, the system, or an admin connection without context cannot write one.
- **Composite keys.** The note names its booking and its author through foreign keys that carry `tenant_id`: a note can name only its own tenant's booking, and only a member of that tenant as its author.
- **The body** is 1 to 500 characters with at least one visible character; line breaks are allowed and other control characters are not. The CHECK refuses every C0 control but the line break, DEL, and the C1 controls (U+0080 to U+009F), and wants one character outside white space, those controls, and the Unicode spaces, joiners, marks, fillers, and variation selectors that show nothing (the same set as the contract's `invisibleCharacters`). It is text a person typed: it never enters an audit row, an event, a log, or the idempotency store, whose kept answer to an added note holds the note's id, author, and time only.
- **Who reads it.** Owners and booking staff hold `notes.read` and `notes.write`; finance holds neither (owner decision, 2026-10-19), as a note can name a guest. Row-level security keeps notes to their tenant; the role check is the API's.

## Waiver evidence (G2.15)

The waiver migration (`*_waivers.sql`, after the self-service migration) adds six tenant-owned tables under rules 1 to 10, described in the [waiver contract](../domain-waivers/README.md):

- `waiver_templates` and `waiver_template_versions`: append-only for every role. A trigger numbers each version after the template's highest, keeps its effective start no earlier than now, and computes its content hash from the canonical text, so no writer chooses it.
- `waiver_requests`: one per participant and version, live (pending or signed) at most once per participant and booking. Its participant is named with the booking in a composite key to `booking_participants`, so a request cannot pair one booking with another's guest. The runtime may UPDATE `state`, `revoked_reason`, and `superseded_by` only; a trigger enforces the one-way states and stamps their times, and a request becomes signed only with its evidence.
- `waiver_deliveries`: append-only. A trigger numbers generations, holds the sending limits (5 generations per request, and `app.waiver_send_refusal`: 10 minutes between sends of one participant's waiver to one address, and caps per participant, address, booking, and tenant), keeps `send_after` no earlier than the insert, and requires the generation's own waiver message in `email_messages`, due no earlier than `send_after`.
- `waiver_signing_sessions`: opened only by the redemption that consumed a waiver link in `guest_access_links` in the same transaction; afterwards the runtime may only revoke one (`revoked_at`, `revoked_reason`).
- `waiver_evidence`: append-only for every role, the owner included. A trigger checks the request, session, signer, version, hash, and acknowledgments; a CHECK holds the PDF to its SHA-256; and at commit evidence stands only beside a signed request.

One new function in schema `app` is callable by the runtime: `app.waiver_send_refusal`, a STABLE invoker function (`search_path` pinned, EXECUTE revoked from PUBLIC and granted to `tidegrid_app` only) that answers whether a waiver email may go now and, if not, when; the service asks it before sending, and the deliveries trigger calls it for every writer. It runs under the caller's row-level security. The waiver triggers run as the writer, under its row-level security, and filter by tenant explicitly.

## Custom hostname lifecycle (G2.14b)

Migration `0011_custom_hostname_lifecycle.sql` adds the lifecycle of a custom hostname. Resolution still reads only `tenant_hostnames.status`; the provider's detail lives beside it. The adapter and the service are in [packages/domain-hostnames](../domain-hostnames/README.md).

- **`tenant_hostname_provisioning`**, tenant-owned, under rules 1 to 10: one row per custom hostname, with the provider (`fake` or `cloudflare_saas`), the provider's record id (unique per provider, stored once), the mapped ownership and certificate states, the public DNS instructions, the last error code, when it was checked and is next due, and the claim's end (seven days, the provider's validation window). It names its hostname with its tenant in a composite foreign key to a new unique key on `tenant_hostnames (hostname, tenant_id)`. The runtime holds SELECT only: 0001's default INSERT is revoked, and no UPDATE is granted. DELETE and TRUNCATE raise for every role, the owner included. A trigger refuses a row for anything but a pending custom hostname of the same tenant, keeps the tenant, name, provider, claim, and a stored provider id fixed, and stamps the times.
- **Transitions on `tenant_hostnames`**, for every role, by trigger: a hostname keeps its name, tenant, kind, and creation time; pending moves to active only for a custom hostname, with its verification time, while its provisioning row holds both provider states `active`; pending or active moves to disabled; a disabled name never moves again, so it stays reserved. No existing fixture updates these rows, so none changed.
- **The `platform` kind**, for an explicit allowlist (`demo.tidegrid.us`) only, written by the admin connection, never swept (G2.14b D19(b), a coordinator default confirmed by the owner on 2026-11-08).
- **`app.resolve_hostname`** keeps its signature and also requires `verified_at IS NOT NULL` for an active row, a second guard on the CHECK in 0002.
- **Name rules.** There is no name-shape trigger on insert, so every existing fixture stays valid. `app.hostname_request`, the only writer of new custom rows, refuses a name that is not normalized, is over 200 characters (an audit subject holds 200), has fewer than three labels, carries a punycode label, or equals or ends on a label boundary in `tidegrid.us`, `workers.dev`, `pages.dev`, `localhost`, `test`, `example`, `invalid`, `onion`, `local`, `internal`, `arpa`, or `alt`. `packages/tenant-config` holds the same rules for the CLI.

Functions, all SECURITY DEFINER under rule 7, with explicit tenant predicates:

| Function | Effect | Runtime EXECUTE |
|---|---|---|
| `app.hostname_sweep_tenants(limit)` | Tenant ids with a provisioned custom hostname whose check is due, or whose pending claim ran out. At most 1,000. STABLE | Yes |
| `app.hostname_record_check(tenant, hostname, provider_id, hostname_state, certificate_state, error_code)` | Records a reading for the transaction's own tenant, only when the provider id equals the stored one. May demote and never promotes: an active hostname is disabled only on a definitive negative (ownership `moved`, `blocked`, or `deleted`, or the certificate `failed`), and a pending one past its claim expires. A `pending` or `unknown` reading, such as a certificate renewing, is recorded and changes nothing. With both states NULL and an error code it records that the provider gave no reading for this one record: the stored states stay, the code is kept, nothing is demoted, and an ended claim still expires; one state NULL, or both with no code, raises 22023. The next check backs off from 60 seconds to 4 hours while pending and comes an hour later while active | Yes |
| `app.hostname_request(tenant, hostname, provider)` | A pending custom row and its provisioning row, after the name rules; refuses a name any tenant holds in any status | No |
| `app.hostname_attach_provider(tenant, hostname, provider_id, instructions)` | Stores the provider's record id and DNS instructions once, for a pending row | No |
| `app.hostname_activate(tenant, hostname, provider_id, hostname_state, certificate_state)` | Pending to active, with both states `active`, a matching provider id, and the claim still open | No |
| `app.hostname_disable(tenant, hostname, reason)` | Any kind to disabled; false when already disabled | No |

Every transition writes an `audit_events` row in the same transaction. Activation is admin-only: if the runtime both wrote provider states and activated, the "both active" check would only repeat what the runtime itself wrote.

**Residual trust.** Provider truth is whatever the adapter reports to the admin CLI or the sweep. The database guards tenant scope, the provider id match, and the transitions; it cannot prove a reading.

**Disabled is terminal, by design.** No function moves a disabled hostname back, and the name stays reserved, so a false demotion cannot be undone from the runtime or the CLI. That is why only a definitive negative demotes, and why the sweep records no reading for a hostname when the provider refuses to answer about it (a rotated token, another 4xx, a malformed answer, a missing zone). Expiring a pending claim that ran out is not a reading: the sweep still does it after such a refusal, and it disables only a name that never went live. If a disabled hostname ever has to come back, the recovery path is a reviewed migration `0012` with an admin-only re-enable function and its audit, not a manual update, which the trigger refuses for every role.

`app.hostname_sweep_tenants` has the same argument as the hold sweep's: it returns tenant ids only, capped at 1,000, read-only and STABLE, and every read and write that follows runs in `inTenantTransaction` under forced row-level security. It reveals that some tenant has a custom hostname with a check due, a weaker signal than the shared id sequences already give. Since 0013 it orders by the `hostname` stamps, which the sweep writes only for tenants it may read the provider for.

## Sweep turns (0013)

Migration `0013_sweep_fairness.sql` adds `sweep_turns`, a tenant-owned table under rules 1 to 10. It has forced row-level security with the `tenant_isolation` policy, the default SELECT and INSERT, and UPDATE on `last_turn_at` and `run_id` only. Triggers refuse DELETE and TRUNCATE for every role, the owner included.

- **Stamps.** A sweep stamps a tenant in that tenant's own `inTenantTransaction` (`recordSweepTurn` in `src/fair-sweep.ts`), before its first turn and again at its first extra turn. A sweep may decline a stamp (`stampWhen`); the hostname sweep does so once it reads the provider no more. A stamp never moves back: of two overlapping runs, the later time stays. A stamp writes no audit or outbox row.
- **The list functions.** The four sweep list functions read the stamps only to order due tenants least recently served first, then by tenant id. They still return tenant ids only. Each joins on its own tenant and its own sweep name explicitly (`t.tenant_id = d.tenant_id AND t.sweep = ...`), because the definer bypasses row-level security (rule 7). - **Tests.** `src/sweep-turns.integration.test.ts` proves the grants, the guards, and the order.

Migration `0014_booking_email_resends.sql` (G2.16b follow-up) holds the staff resend limits for every writer, not only the service. The service and its lock order are in the [booking contract](../domain-booking/README.md#staff-resend-of-a-bookings-email-g216b). Decisions D1 to D11 are coordinator defaults, confirmed by the owner on 2026-11-08 ([decision register](../../docs/v2/06-decision-register.md#2026-11-08-owner-confirmation-of-the-coordinator-defaults-owner-decisions)).

- **`booking_email_resends`**, tenant-owned, under rules 1 to 10: one row per staff resend, with its booking, its generation (1 to 999999999, the last part of its message's key), its kind (`confirmation` or `cancellation`), its message, its time, and who asked (`actor_type`, `actor_id`, `api_request_id`, D1 B). Forced row-level security with the `tenant_isolation` policy. It names its booking and its message in composite foreign keys that carry `tenant_id`. The runtime keeps the default SELECT and INSERT and receives nothing more; UPDATE, DELETE, and TRUNCATE raise for every role, the owner included (`app.reject_mutation`).
- **`app.booking_resend_facts(tenant, booking, at)`**, a STABLE invoker SQL function (`search_path` pinned, EXECUTE revoked from PUBLIC and granted to `tidegrid_app` only), counts the ledger by D4's rules: the booking's deliverable resends (not canceled, or attempted at least once), its newest of any state (to the millisecond), the operator's resends of any state stamped after the hour before `at`, and when the 50th newest is an hour old. No count has an upper bound on the row's time, so a row stamped after `at`, by a writer that committed while the caller's transaction was open, still counts. The service reads it, and so does the trigger (D2 A). Row-level security applies inside it, and it filters by tenant explicitly; the catalog suite pins it, and every 0014 function, as invoker.
- **The check trigger** (`app.check_booking_email_resend`, a VOLATILE invoker function, before insert) stamps the time and the actor from the transaction, whatever the insert names; refuses any isolation level but READ COMMITTED (SQLSTATE 25000), since a snapshot taken before the lock could pass a limit (D7 A, as 0006 refuses capacity changes); takes the tenant's resend lock, `pg_advisory_xact_lock(hashtextextended('tidegrid.booking_resend:' || tenant, 0))`, the key the service takes first, in its own statement; refuses a transaction that has run past its bound (`_late`, below); requires the booking's next generation (`booking_email_resends_sequence`) and the message this transaction queued for that booking, generation, and kind, still queued and unattempted (`booking_email_resends_message`); then refuses a 6th deliverable resend (`_limit`), one within 10 minutes of the newest (`_interval`), and a 51st in the operator's hour (`_rate`), all SQLSTATE 23514. The message insert's lock (below) already gives the ledger statement a snapshot taken after the lock was granted; the trigger's own second take of the lock, and its being VOLATILE so each of its statements takes a fresh snapshot, are a second line.
- **One instant, and a 30 s bound** (fix round, coordinator decision A of 2026-11-01). The row is stamped, and the limits are decided, at the transaction's time, `date_trunc('milliseconds', now())`: the instant and the precision the service decides at, and the time its message carries, so the service, the trigger, and the messages read agree at every boundary. A transaction's time is its start, so a writer that held its transaction open would carry an old stamp past the 10 minutes and the hour (review probe P6). A resend whose transaction has run longer than `app.booking_resend_max_transaction()` is therefore refused, after the lock at its ledger insert and again at commit (`booking_email_resends_late`, SQLSTATE 23514). The bound is 30 s. A transaction may shorten it with `app.resend_max_transaction`, never lengthen it; an empty value means 30 s, and a malformed or negative one closes it (`app.booking_resend_max_transaction`, a STABLE invoker function the runtime may execute). So a stamp lags its commit by at most 30 s, and that is the slack against the 10-minute and hourly rules: measured by commit times, a resend may commit as little as 9 minutes 30 seconds after the booking's previous one, and 51 of the operator's resends may commit within 59 minutes 30 seconds. Those figures hold for the service and for any writer that does none of the following. The commit check bounds the stamp only up to the moment its deferred event runs; any wait after that, before the commit record, is unbounded, and that is a class, not one escape (final check of 2026-11-01): a deferred foreign key whose referenced row another session holds `FOR UPDATE` (such as 0010's `waiver_requests_superseded_by_fkey` or 0009's `booking_cancellations_refund`; the check's probe let two resends commit 45 ms apart), `PREPARE TRANSACTION` where `max_prepared_transactions` is above 0 (the bound relies on it being 0, and the catalog suite fails if it is not), and `SET CONSTRAINTS ... IMMEDIATE`. Each needs a writer with `tidegrid_app`'s credentials that bypasses the service, the same threat class as before; the service does none of them. Bounding sends at the delivery claim instead is a possible pre-pilot follow-up. A service resend measured locally runs about 20 ms, and the 20th of 20 at once on one tenant about 450 ms, queued on the tenant's lock; one that does run past the bound rolls back whole and is answered 503 `booking_email_busy` by the route.
- **The lock at the message** (`email_messages_staff_resend_lock`, `app.lock_booking_resend`, before insert on `email_messages` for keys starting `booking.resend:`) takes the same resend lock before the message's key is claimed. For the service it is a no-op. A writer that bypasses the service waits there for a service resend in progress, holding no resend key, instead of claiming a key the service is about to claim and then waiting for the lock the service holds: the review reproduced that deadlock, with the staff request aborted (probe P1).
- **The deferred check** (`email_messages_staff_resend`, a constraint trigger on `email_messages`, deferred to commit) refuses a message whose key starts `booking.resend:` without its ledger row (D4 A), or whose transaction has run past its bound (`_late`). The waiver ledger has no such check; this one closes the bypass of writing the message alone. A build from before 0014 writes no ledger row, so its staff resends fail at commit until it is rolled forward (owner item O3).
- **Backfill.** The file refuses to run unless its role bypasses row-level security (the 0009 guard), writes one ledger row per existing `booking.resend:` message (generation from the key, kind from the template, the message's time, actor `system`), refuses any key that does not parse strictly, names another booking, or carries another template, and checks the counts match. `src/migrate-0014.integration.test.ts` proves it on scratch databases. A request in flight that already holds a row lock on `email_messages` or `bookings` can deadlock with the file, and either may be aborted; apply it before the API release that uses it, in a quiet window (O2). The file rolls back alone, and a rerun is safe.
- **Not held here.** The service's eligibility refusals (D5 A); the two templates' other keys (D4 C, proposed); the waiver ledger's `send_after` hole (D6, recorded only).

## Staff resend claims (0017)

Migration `0017_resend_bound_at_claim.sql` (W1-RESEND-CLAIM; provisional number, claimed at merge, `0018` reserved) holds the staff resend limits at the delivery claim, the moment an email starts towards the provider, for every writer. The owner pulled it forward on 2026-11-08 (O-SCOPE item 2 in the [decision register](../../docs/v2/06-decision-register.md)). Its choices are coordinator defaults, pending owner confirmation.

- **Why.** 0014 decides the limits on the ledger's stamps, and its commit check bounds a stamp only until that check runs. A writer with `tidegrid_app`'s credentials that waits after it (a deferred foreign key held by another session, or `SET CONSTRAINTS ... IMMEDIATE`) commits a resend with an old stamp. Its email then goes out beside resends stamped later: two emails to one guest seconds apart, or more than 50 of the operator's in one hour. The 0014 section above calls this class unbounded.
- **`booking_email_resend_claims`**, tenant-owned, under rules 1 to 10: one row per claim of a `booking.resend:` message, with its booking, its message, the attempt the claim began, and `claimed_at`. Forced row-level security with the `tenant_isolation` policy; composite foreign keys to its booking and its message. The runtime keeps the default SELECT and INSERT; UPDATE, DELETE, and TRUNCATE raise for every role (`app.reject_mutation`). Its insert trigger (`app.check_booking_email_resend_claim`, VOLATILE invoker) takes the tenant's resend lock, stamps `claimed_at` at `clock_timestamp()` whatever the insert names, and requires a `booking.resend:` message of that booking (`booking_email_resend_claims_message`). A direct insert only adds to what the limits count. The file backfills one row per resend message already attempted, at its latest attempt's time.
- **The rules** (`app.booking_resend_claim_refusal(tenant, message, at)`, a STABLE invoker SQL function the runtime may execute, `search_path` pinned). For a `booking.resend:` message it returns one row when a claim at `at` must not go ahead: `resend_unrecorded` (no ledger row) and `resend_limit` (5 other resends of the booking deliverable, by 0014's count) never lift; `resend_interval` (another resend of the booking claimed in the last 10 minutes) lifts 10 minutes after that claim; `resend_rate` (50 other resends of the operator claimed in the last hour, each message once) lifts when the 50th newest is an hour old. A message's own earlier claims never bar it, so its retries and the 0015 give-back keep their timing.
- **The claim guard.** `app.check_email_message()` is replaced in place, as 0015 did: same name, owner, settings, and trigger, with 0015's text unchanged around one new step in the claim branch. A claim of a `booking.resend:` message (the first or any later one) is refused under REPEATABLE READ or SERIALIZABLE (SQLSTATE 25000), takes the tenant's resend lock, is decided at `clock_timestamp()` once the lock is held, raises 23514 `email_messages_<rule>` on a refusal, and otherwise writes its log row.
- **Why it holds.** Only the delivery job sends, right after its own short claim commits, and each claim logs the clock it was checked at. A claim a bypass writer holds open logs an early time but sends nothing, and while open it holds the tenant's resend lock, so nothing else is written or claimed; its message goes out only through a later claim, checked and logged at that time.
- **Lock order.** The delivery job takes the tenant's resend lock before it locks any message, as the resend service does, so the two never deadlock. It only tries the lock: while another transaction holds it, that run claims nothing for the tenant, so a held lock delays the tenant's mail to a later run and never stalls the sweep. A bypass writer that locks a resend message first can still deadlock with a service resend; PostgreSQL detects it.
- **The service path.** A resend is claimed within seconds of its write, which 0014 already spaced, so it goes out as before. It waits only when real sends would break a limit: after a backlog (an outage, or a missed delivery run), or when the booking's previous resend was retried less than 10 minutes before. It goes out at the next delivery run after the wait.
- **Not held here.** A writer that forges the 0015 give-back after a send can make the delivery job send the same message again; that applies to every message, not only resends, and is recorded as a residual. The claim log's stamp can still lag a send: its foreign key checks run after the stamp, and a writer that holds the booking row can make the claim wait there. The delivery run's own deadline bounds that lag (about 20 s for the sweep, at most 30 s after a request), close to 0014's 30 s slack. The 0014 residuals D4 C, D5 A, and D6 are a separate goal (W1-0014-RESIDUALS). No column, index, or row changes on `email_messages`.
- **Applying it.** Apply it right before the API release that carries the matching delivery job, and keep the window short (no staff resends in it, if possible). An older job does not take the tenant's resend lock before it locks a message, so a claim of a resend can deadlock with a service resend, and it does not skip a resend that must wait: it meets the guard's error instead. Such a resend sorts first in the queue, so every delivery run for that tenant fails, for all of its mail, until the wait lifts (up to an hour) or the new job is released. Tests: `packages/domain-booking/src/adversarial/staff-email-resend-claim.integration.test.ts` (C1 to C10).

A writer with `tidegrid_app`'s credentials can still record a made-up event for its own tenant's sent message: the residual, since the runtime is trusted to record what the queue gave it.
- **The message itself does not change.** It stays `sent` (the provider did accept it), so 0009's delivery rules, 0014's limits, and 0017's claims are untouched. Staff reads join the applied event.
- **Unknown ids, `email_events_unmatched`.** A platform table under rule 6: row-level security forced with no policy, every privilege revoked from the runtime, its identity sequence included. It is not append-only, so the owner can prune it: anything that can publish to the queue can add rows. `app.record_unmatched_email_event(...)`, a SECURITY DEFINER function with `search_path` pinned, inserts one row per provider event id and answers whether it was new. It has no tenant and joins nothing; no reader exists yet.
- **The index (0022).** `email_messages_provider_message_once`, unique on `(provider, provider_message_id)` where the id is set, built `CONCURRENTLY` in a no-transaction file: the first file in the tree to use that mode (below). The resolver relies on it to answer one row. If two sent messages ever shared an id the build fails and leaves an invalid index; follow the repair below. Apply 0021 and 0022 together, before the API release that carries the consumer.

## Delivery foundation (0023)

W3-G2.3 publishes the outbox to a queue and consumes it in an async handler. PostgreSQL stays the record of truth: a queue message names one event by tenant and id and carries no payload. Code: `src/delivery.ts`; the Worker's consumer: `apps/api-worker/src/delivery.ts`. Coordinator defaults, pending owner confirmation, are in the [decision register](../../docs/v2/06-decision-register.md).

- **Delivery columns.** `outbox_events` gains `delivered_at`. The runtime may update `published_at`, `delivered_at`, `available_at`, `attempts`, and `last_error`, and nothing else: a trigger refuses any change to an event's content, and no role deletes or truncates one. `last_error` is a short code, never a message. Events written before 0023 are marked published and delivered by the migration, so the first publisher run sends no history.
- **Publication.** The cron's fifth job sends due events with fair turns per tenant (`app.outbox_publish_tenants`, sweep name `outbox` in `sweep_turns`). A row is marked published only after the queue accepted its batch. A refused send leaves the batch as it was, with no attempt counted, and due again in five minutes, so a queue outage never makes dead letters. Events with an open dead letter are left out of the publisher's query and tenant list, so they never hold back newer events. A published event not delivered within 15 minutes, with no open dead letter, is a lost hint and is sent again; after 10 sends it becomes a dead letter with source `publisher`. Without an `OUTBOX_QUEUE` binding the job is skipped.
- **Outcomes.** `outbox_deliveries` holds one append-only row per event and handler, written in the handler's own tenant transaction after a per-event advisory lock. A duplicate, a retry, or a replay finds the row and skips that handler. Delivery is at least once: a handler's effect outside the database may repeat if the process dies before its commit.
- **Dead letters.** `outbox_dead_letters` records a message that exhausted its retries: the event, its topic, the failing handler when known, a short error code, the attempts, and the source (`consumer`, `queue`, or `publisher`). Never a payload. At most one is open per event. Rows are never deleted; a replay sets `replay_reason` once and the trigger stamps `replayed_at` and `replayed_by` from the transaction's actor, which must be a person (a system job is refused). A late queue report about an event already delivered records nothing. While a dead letter is open, a late or duplicate hint runs no handler and leaves the event undelivered (the consumer reports it `parked` and acks); only a replay reopens it. Each hint carries `replays`, the count of the event's replayed dead letters when it was sent, so a report from a copy older than the last replay is `stale` and records nothing. The publisher dead-letters an exhausted event after its own transaction, through the same locked path. Handler runs, completion, recording, and replay all take the same per-event advisory lock first, so an event is never both delivered and parked. `app.outbox_dead_letter_tenants` lists tenants with open dead letters.
- **Replay.** `pnpm --filter @tidegrid/database outbox:dlq list`, then `outbox:dlq replay --tenant <uuid> --id <id> --operator <name> --reason <text>`, which prints what it would do; add `--go` to run it. A replay writes an audit row with the reason and makes the event due again; only handlers without an outcome run.
- **Cleanup.** `app.delivery_cleanup(limit)` is a definer function the cron calls last. It deletes, across tenants, completed idempotency keys and quotes that no checkout or order names, each seven days past its expiry, at most `limit` (1 to 5,000) of each per call. The runtime holds no DELETE. Quotes, their lines, and their taxes stay append-only for updates; a delete passes their guard trigger only inside this function, and only for a quote a week past expiry.

- **Places keep their numbers.** A party's places are 1 to the party size it was sold with (its checkout's, which never changes), less the places given up, so a change not yet applied in the same transaction never opens an extra place. A participant joins only at one of them, and never at a place given up (`booking_participants_removed`, `booking_participants_party_size`); `app.check_booking_participant` is replaced for this.
- **Removed participants stay.** `booking_participants` gains `removed_at`, set once by the trigger's clock and only with the party change naming the participant, with nothing else changing (`booking_participants_removed`). A removed participant never changes again. The row stays for the waiver and message history that names it. The runtime gains UPDATE on `booking_participants (removed_at)`.
- **The booking follows its change.** `app.check_booking_lifecycle` is replaced as in 0034, except that a booking's `party_size` and `hold_id` may change together, down by one, while it stays confirmed and on its trip, with a party change row naming the old hold and size whose own hold (`booking_party_change:<change id>`) is confirmed for the new size. The runtime gains UPDATE on `bookings (party_size)`.
- **The old hold may be released.** `app.check_booked_hold` (0007) is replaced: a confirmed hold behind a confirmed booking still keeps its seats, unless a party change names it as the hold it gives back. The service releases it before taking the smaller hold, under the trip's lock, because on a full trip the smaller hold would not fit beside it.
- **Checked at commit.** A deferred constraint trigger (`booking_party_changes_applied`) requires the old hold released, the booking on the change's own hold (confirmed, or released by the booking's cancellation; or that hold since given up by a later change or move), and the participant at the place, if any, marked removed. 0034's move check (`app.check_rescheduled_released`) is replaced the same way, so a move followed by a party change in one transaction commits.
- **Row-level security and guards.** Tenant-owned under rules 1 to 10, append-only (no UPDATE, DELETE, or TRUNCATE for anyone), composite tenant foreign keys. No index on a pilot-volume table: the new column has none, and the new table's own index is created with it.
- **Applying it.** Apply before the API release that carries this goal. An older API keeps working: no place is given up without the new code, so `removed_at` stays null and every party's places are 1 to its size, as before.
- **Tests.** `packages/domain-booking/src/party-changes.integration.test.ts`, `packages/domain-waivers/src/waivers.integration.test.ts` (a removed participant's waiver), and `apps/api-worker/test-integration/party-changes.integration.test.ts`; the catalog test in `src/tenancy.integration.test.ts` pins the privileges.

## Indexes built concurrently (no-transaction files)

The runner has a second mode for `CREATE INDEX CONCURRENTLY`, which PostgreSQL refuses inside a transaction. It is the D6 A standing rule of the pre-pilot hardening goal, confirmed by the owner on 2026-11-08 ([decision register](../../docs/v2/06-decision-register.md#2026-11-08-owner-confirmation-of-the-coordinator-defaults-owner-decisions)): the mode lands before any pilot-volume table gets a new index. The marker, the one-statement rule, the repair rule, and leaving the 0005 constraints alone (D1 to D4) are coordinator defaults, pending owner confirmation ([decision register](../../docs/v2/06-decision-register.md#2026-11-08-w1-mig-conc-a-no-transaction-runner-mode-for-create-index-concurrently-owner-go-coordinator-defaults-pending-owner-confirmation)). Update, 2026-11-08: `0022_email_events_index.sql` (W1-EMAIL-EVENTS) is the first file that uses the mode, `0030_refunds_pending_index.sql` (W3-G2.9) the second, and `0032_payments_check_index.sql` (W3-G2.10) the third.

- **The marker (D1).** A file whose first line is exactly `-- tidegrid:no-transaction` runs outside a transaction. Every other file runs in one transaction, exactly as before. The marker anywhere else, misspelled, or any other `-- tidegrid:` or `/* tidegrid:` directive anywhere in the file, after SQL on the same line included, fails the run before anything is applied, so a file meant for this mode never runs in a transaction by accident. A line comment ends at a carriage return as well as a line feed, as in PostgreSQL, so no SQL hides behind a bare CR.
- **One statement (D2).** A marked file holds exactly one `CREATE [UNIQUE] INDEX CONCURRENTLY` statement, with comments as needed. Nothing else is accepted, not even `DROP INDEX CONCURRENTLY` or `REINDEX ... CONCURRENTLY`. The runner reads the file conservatively: dollar quotes, parameters, escape strings (`E'...'`), backslashes inside strings, and unterminated quotes or comments are refused rather than parsed. Every file is checked before the connection opens. Write `IF NOT EXISTS`, so a rerun after a lost connection between the build and its record only records the file.
- **Timeouts.** The statement runs under session-level `SET lock_timeout` and `SET statement_timeout`, the same values as the transactional files (5 s and 120 s, or `TIDEGRID_MIGRATE_LOCK_TIMEOUT_MS` and `TIDEGRID_MIGRATE_STATEMENT_TIMEOUT_MS`), reset when the file ends. The lock timeout also ends the build's waits for other transactions: for a writer still holding the table, and for any transaction in the database whose snapshot is older than the build's, whatever it reads. Both are tested. So on a busy database a long transaction anywhere can fail a build, which then leaves an invalid index (below). A large table may need a longer statement timeout, set for that run only. The session settings never reach a build on another session: the client reconnects silently only when a connection closes while idle, and the runner hands the build to the connection in the same turn the last `SET` returns, so a connection lost there fails the file instead. A test cuts the connection at that point.
- **Recorded only after success.** The file is written to `schema_migrations` after the statement succeeds, in its own autocommit statement. A failure leaves it unrecorded, so it runs again next time.
- **An invalid index blocks every run (D3).** A failed or canceled concurrent build leaves its index behind, marked invalid: a duplicate under a unique index, a lock or statement timeout, a deadlock, a lost connection. Each run, under the advisory lock and before it applies anything, looks for invalid indexes outside the system catalogs and temporary schemas, whether or not a file is pending. If it finds one it refuses, names each index, and prints the repair command. It never drops anything. Partitioned indexes are not checked: they cannot be built concurrently, and one created `ON ONLY` a parent is invalid by design until its partitions attach. An index another session is still building also counts as invalid, so wait for it and run again.
- **The runners' lock is polled.** Runners serialize on the advisory lock with `pg_try_advisory_lock` every 250 ms, not a blocking `pg_advisory_lock`. A runner blocked inside a statement holds a snapshot, a concurrent build waits for every older snapshot, and the two deadlock; `migrate.integration.test.ts` showed that with the blocking call.
- **Not covered.** The 0005 constraints are not rebuilt concurrently (D4). No production index is added here. Rule R4 of the wave 1 goals still holds back any new index on `email_messages`, `payments`, `payment_refunds`, `bookings`, `booking_participants`, or the waiver tables until this mode is on `main`.

### Repair after a failed concurrent build

1. Read the failed run's error. It names the file, the cause, and each invalid index with its `DROP INDEX CONCURRENTLY IF EXISTS` command. A later run prints the same commands.
2. As the admin role, run each printed command on its own, outside a transaction (in `psql`, one statement per line, no `BEGIN`). On Neon main that is a live step and takes the owner's go, as every Neon main migration does.
3. Fix the cause: remove the duplicates a unique index found, wait for the long transaction that held the lock, or raise the statement timeout for this run.
4. Run the migrations again. The file was not recorded, so it runs again from the start.

If the build succeeded but the file was not recorded (the connection dropped between the two), the index is valid and no run refuses. A file written with `IF NOT EXISTS` then only records itself on the next run. One without it fails with "already exists"; drop the valid index concurrently and run again.

Tests: `src/migrate.unit.test.ts` covers the marker, the one-statement rule, the timeouts, and the repair message. `src/migrate.integration.test.ts` proves the mode on scratch databases with test-only fixture migrations in `test-fixtures/no-transaction-migrations/`: a marked file applies outside a transaction and is recorded once; the same statement unmarked fails inside its transaction; a duplicate key, a lock timeout on a writer, a lock timeout on an older snapshot, and a statement timeout each leave an invalid index and no record; later runs refuse with the repair and keep the index; the printed repair and a rerun apply the file; a second runner waits for the lock without stalling a build; and a connection cut right after the session timeouts fails the file with nothing built, recorded, or locked.

- `tools/local-db/local-db.sh` is the throwaway database, on a Mac and in CI alike. It runs the official `postgres` 17 image, pinned by digest, on `127.0.0.1:55432` with podman (CI uses Docker; set `TIDEGRID_LOCAL_DB_ENGINE` to choose). `up` starts a fresh container and prints `DATABASE_URL` and `TIDEGRID_EPHEMERAL_DB=1`; `prepare integration|guest-e2e|console-e2e` migrates and seeds for one CI job; `down` removes it. `pnpm test:local-db` runs every integration suite, the guest browser parts A and B, and the console browser tests, each part on a fresh container, as each CI job has a fresh database. It moves an existing `apps/api-worker/.dev.vars` aside and restores it at the end. On a Mac the podman machine must be running (`podman machine start`); keep the Mac awake while it runs. `eval "$(tools/local-db/local-db.sh env)"` exports the two variables into the shell, after it checks that the container on that port is this checkout's.
- Clock check: `up`, once the server is ready, and `test`, before its first part, refuse a container clock more than 5 s away from the host's. A quote's `expires_at` comes from the writer's clock (Node, in the tests) while checkout compares it with the database's `now()`, so a container clock that lags makes a back-dated quote look fresh. A podman machine on a Mac can lag by many minutes after the Mac sleeps; its time daemon corrects that only once it reaches a time source. Fix it at once with `podman machine ssh sudo chronyc makestep`, or restart the machine; for Docker, the engine's VM clock is off and restarting the engine resyncs it. Docker on a Linux runner shares the host clock, so in CI the check passes. The integration tests that back-date a quote, or compare a database timestamp with the current time, read `now()` from the database rather than `Date.now()`; product code still mixes the two clocks in places (waiver send times), which the check guards.
- Parallel lanes: two checkouts can run integration suites at once with distinct `TIDEGRID_LOCAL_DB_NAME` (starting `tidegrid-local-db`) and `TIDEGRID_LOCAL_DB_PORT` values. The script refuses to remove a container that another checkout started. The browser parts use fixed ports, so only one checkout at a time runs them.
- The container's admin is a true superuser, while Neon's owner is not, so a permission that only Neon refuses can pass locally and in CI.
- `pnpm --filter @tidegrid/database neon:branch create <name>` makes an optional throwaway Neon branch, when the Neon project has quota. It expires after six hours, and its compute autoscales from 0.25 to 1 CU. The project default is a fixed 0.25 CU, which the race suites ran out of memory. It prints only the branch id. Pass `--out <file>` to receive the admin connection string in a new file with mode 0600; it is never printed. `--ttl <hours>`, `--no-expiry`, and `--no-endpoint` shape a backup branch, such as the release runbook's restore point.
- Close every postgres.js client with a timeout, `end({ timeout: 5 })` unless there is a reason for another value. Without one, `end()` can wait forever. It does so on a query still running, and on a connection whose peer went silent (a sleeping host, an expired NAT entry, a dropped path). One such connection becomes a 120 second hook timeout or a setup that never finishes. In a Worker it holds the connection until the runtime cancels the `waitUntil`. `createDb().end()` is already bounded; call it once the handle's work is done. `connection-loss.integration.test.ts` covers both cases; the silent peer is a relay that drops traffic. It runs on the local container and in CI, and skips on a remote host such as Neon.

## Neon main guard

Integration setup and `app-role:password` both rotate `tidegrid_app`'s password. On Neon main that breaks Hyperdrive (rule 4 of the [Nov 1 runbook](../../docs/runbooks/2026-11-01-preview-deploy.md)). The guard in `src/testing.ts` refuses it ([decision register](../../docs/v2/06-decision-register.md), 2026-11-08, coordinator defaults pending owner confirmation).

- **The recorded host.** `NEON_MAIN_HOST`, a bare host name, in the environment or in the repository root `.env.local` (gitignored). Never commit it. A value that is not a bare host name refuses every run until it is fixed.
- **Integration suites.** `integrationAdminUrl()`, which the shared global setup calls, and `prepareIntegrationDatabase()` refuse the recorded host, even with `TIDEGRID_EPHEMERAL_DB=1`. With no host recorded, they refuse every Neon host unless `TIDEGRID_NEON_BRANCH=1` marks a throwaway branch. The local container and CI are unaffected.
- **`app-role:password`.** It refuses the recorded host unless `--neon-main` is given (`pnpm --filter @tidegrid/database app-role:password -- --neon-main`). With no host recorded, a Neon host needs `--neon-main` or `TIDEGRID_NEON_BRANCH=1`. It refuses `--neon-main` for a database that is not the recorded host, and for a multi-host URL that lists any other host beside it, since postgres.js tries each host in turn. Hosts are compared both as written and as a resolver reads them, percent-decoded and IDNA-mapped, so a spelling such as an ideographic full stop or fullwidth letters counts as the main host. `--neon-main` takes only the plain spelling.
- **A throwaway branch.** `neon:branch create` prints, on stderr, the flags its branch needs: `TIDEGRID_EPHEMERAL_DB=1 TIDEGRID_NEON_BRANCH=1`. A branch's host never equals main's, so once `NEON_MAIN_HOST` is recorded the branch flag is no longer needed.
- **Matching.** Every host a postgres.js client would reach counts: each host of a multi-host URL, else `PGHOST`, else localhost. The guard joins a WHATWG parse with a copy of the installed postgres.js parser (first `@`, `#` not a delimiter, the host list percent-decoded), so a crafted URL cannot hide a host that postgres.js would try. A unit test checks nine fixed URLs, the crafted ones and the ordinary forms, against the installed client: every host it lists must be one the guard counts. It does not prove the copy matches on other URLs, so a postgres.js upgrade that changes parsing only elsewhere passes. Recheck the copy when the lockfile moves postgres.js off 3.4.9. Hosts compare in lower case without a trailing dot. A pooled endpoint (`-pooler`) compares as its direct endpoint.
- **Messages.** A refusal names the rule and the flag. With no host recorded, `--neon-main` on a host that is not Neon is refused as not a Neon host. It never prints a host, a user, a password, or the URL.
- **Limits.** It compares names only. It does not ask Neon which branch a host belongs to, so a main host recorded wrong, or a main endpoint renamed, is not caught. The `nov1 db` commands have their own refusals.

## The dock QR lookup (0043)

W3-G2.15-rest, owner decision 2026-11-13. `waiver_dock_lookups` records every counted try at the generic dock QR's lookup. Its insert trigger (`app.check_waiver_dock_lookup`) stamps the time, the client (`app.waiver_dock_client_key()`: `app.source_ip`, with an IPv6 address cut to its /64 and an IPv4-mapped one kept whole), and the actor, and refuses a writer that is not a guest (`waiver_dock_lookups_actor`). `app.waiver_dock_refusal(code, matched)` takes advisory locks on the client and the code, and for a miss the operator, and counts: 20 misses from one client in 15 minutes, 8 misses for one code in 24 hours, 300 misses at the operator in an hour (holding misses only), and 100 matches from one client in an hour; the trigger calls it again and refuses past a limit (`waiver_dock_lookups_limit`). A match must name a confirmed booking with that code whose trip departs today in its own time zone and has not ended (`waiver_dock_lookups_booking`); its secret lasts 15 minutes. Retention (`0050`): `app.waiver_dock_cleanup(limit)`, a definer function the runtime may call and the cron calls as its own step, deletes tries more than 30 days old that started no signing, and on those that did (a signing link names them) replaces the client with `redacted`; the signature's own evidence is unchanged. Its guard trigger (`waiver_dock_lookups_cleanup_only`) refuses any other UPDATE or DELETE, and any change to a row under 30 days old; the runtime holds neither privilege, and a role that does (the owner) could set the cleanup's mark itself, as with `0023`. The last-name comparison is the service's.

`waiver_assisted_links` gains the mode `dock_lookup`: started by the guest, with no staff member, naming a matched lookup of the same booking still in its 15 minutes whose trip departs today and has not ended (`waiver_assisted_links_dock`), at most 30 for one lookup, with `identity_checked` false (a staff row keeps true: `waiver_assisted_links_identity_checked`); the staff modes keep 0020's rules (`waiver_assisted_links_actor`). Evidence from a dock link must record `dock_lookup`, the match method `booking_lookup`, no staff member, and no address (`waiver_evidence_method`, and the `waiver_evidence_method_shape` check). Sessions keep 0020's 15-minute rule.
